Attack this. A read-only parity check that will be run against a production Mac mini. Be brief — the two or three things actually wrong, not a survey.

## What it is for
`rc-backend` runs on a Mac mini ("friday") as six user LaunchAgents (`com.fleet.*`). The repo holds the canonical plists in `rc-backend/tools/`. Nothing until now compared what is installed on the box with what is in the repo.

Two things happened the same day that motivated it, both measured:
1. A separate directory (`~/rc-observer/`) fell outside the deploy script's scope, so the host ran a script **139 lines / 22 days** older than the repo. It failed a lookup and fired a "monitoring is broken" alert into the owner's Discord **every day** until it was noticed by someone diffing md5 by hand.
2. `com.edith.log-rotate-check` has a plist sitting in `~/Library/LaunchAgents/` but does **not** appear in `launchctl list`. Installed is not the same as running.

On its first run the check found real drift: `com.fleet.rc-ota.plist` differed, and the difference was one line **inside an XML comment** — the host's copy still named an install path (`rc-backend/launchd/`) that no longer exists. Harmless in itself; the point is that nothing would have told anyone.

## The script

```bash
set -uo pipefail
HERE=<rc-backend/tools>
HOST="${RC_FLEET_HOST:-athenas}"
TEMPLATE_ONLY="com.fleet.rc-health-observer"   # repo only has a .example template

repo_names=()                                   # glob, not a hand-written list
for p in "$HERE"/com.fleet.*.plist; do repo_names+=("$(basename "$p" .plist)"); done
[ ${#repo_names[@]} -eq 0 ] && exit 2

remote="$(ssh -o ConnectTimeout=15 -o BatchMode=yes "$HOST" '
    cd "$HOME/Library/LaunchAgents" || exit 9
    for f in com.fleet.*.plist; do printf "MD5 %s %s\n" "$(md5 -q "$f")" "${f%.plist}"; done
    launchctl list | awk "/com\\.fleet\\./ {printf \"LOADED %s\\n\", \$3}"
' 2>/dev/null)"
rc=$?
[ $rc -ne 0 ] || [ -z "$remote" ] && exit 2      # cannot measure != match

for name in "${repo_names[@]}"; do
    want=$(md5 -q "$HERE/$name.plist"); got=$(awk '$1=="MD5" && $3==name {print $2}')
    case "$got" in [0-9a-f][0-9a-f]*) measured=$((measured+1));; esac   # count only a valid md5
    [ -z "$got" ]        && { echo "NG $name — not on host"; fail=1; continue; }
    [ "$got" != "$want" ] && { echo "NG $name — drift"; fail=1; continue; }
    is_loaded "$name" && echo "ok $name" || { echo "NG $name — matches but NOT loaded"; fail=1; }
done

# a job on the host with no repo counterpart: name it, never delete it
for name in $(remote_names); do
    [ "$name" = "$TEMPLATE_ONLY" ] && continue
    case " ${repo_names[*]} " in *" $name "*) ;; *) echo "?  $name — on host, not in repo"; fail=1;; esac
done

# the template-only one: print that it is deliberately NOT compared, but still check it is loaded
...
[ "$measured" -ne "${#repo_names[@]}" ] && exit 2   # partial measurement != parity
exit $fail
```

Exit codes: 0 = all match and all loaded / 1 = drift or not-loaded / 2 = **could not measure** (deliberately not folded into 0).

## Attack these specifically

1. **md5 over a whole plist file is the comparison.** It flags a changed XML comment as drift — which is what just happened. Is that the right granularity for a *production* check, or does it guarantee the check gets ignored as noisy? Would comparing parsed values (`plutil -convert json` then diff the dict) be better, or does that lose the thing worth catching?

2. **`launchctl list` parsing.** I take column 3 as the label from lines matching `com\.fleet\.`. Is that stable across macOS versions and across job states? Is there a case where a loaded job is absent from `launchctl list` output, or present under a different form, that would make me print "NOT loaded" for a healthy job — i.e. a false red on production?

3. **The `TEMPLATE_ONLY` escape hatch.** One job is excluded from content comparison because the repo only ships a `.example`. That is exactly the shape of an exclusion that quietly grows. Is printing `-- not compared` enough, or should the check instead compare the *structure* of the installed plist against the template (same keys, ProgramArguments pointing into the expected directory) so the exclusion is not total?

4. **What it does NOT check, and whether that makes it misleading.** It does not verify that the program named in `ProgramArguments` exists on the host, nor that the `StandardOutPath` directory is writable, nor that the running process was started from the current plist (a job loaded before an edit keeps the old definition until reloaded — so "matches + loaded" can still mean the *running* job differs from the file). Is that last one severe enough that "ok" is a misleading word here?

5. Anything about running this unattended against a production host that I am underweighting. If the honest answer is "this check gives false confidence, and the real fix is to deploy plists from the repo rather than compare them after the fact", say that.

## launchctl 基本操作

### サービス一覧確認

```bash
# 全launchd jobを表示
launchctl list | grep -i "auto\|bot\|slack\|discord\|openclaw"

# 特定サービスの状態
launchctl list com.example.servicename
# → PID列が数値: 稼働中 / "-": 停止中
# → Status列が0以外: 異常終了
```

### サービス再起動

```bash
# 停止してから起動（確実な再起動）
launchctl unload ~/Library/LaunchAgents/com.example.servicename.plist
launchctl load ~/Library/LaunchAgents/com.example.servicename.plist

# または kickstart（launchd 2.0以降）
launchctl kickstart -k gui/$(id -u)/com.example.servicename
# -k: kill & restart
```

### plistファイルの場所

```bash
# ユーザーのLaunchAgents
ls ~/Library/LaunchAgents/

# システムのLaunchDaemons（要sudo）
ls /Library/LaunchDaemons/
```

現行 man page 上、第3列は Label で、停止中の定期 job も PID `-` で残ります。ただし SSH セッションの暗黙 domain と `~/Library/LaunchAgents` の GUI domain は同一とは限りません。後者はログインユーザー向けです。[Apple Support](https://support.apple.com/guide/terminal/script-management-with-launchd-apdc6c1077b-5d5d-4d35-9c19-60f2397b2369/mac)

[現在の `list | awk`](/Users/tomtim/Infra/mobile-work/rc-backend/tools/fleet-plist-parity-check.sh:62) はやめ、既存の [delivery-check と同じ `launchctl print gui/$uid/$label`](/Users/tomtim/Infra/mobile-work/rc-backend/tools/delivery-check.sh:43) にすべきです。加えて現在の pipeline は `launchctl list` が失敗しても `awk` が 0 を返し、全件を「NOT loaded」にする false red があります。

2. 「file一致 + loaded」は有効中の定義一致ではありません  
plist 編集後に reload されていなければ、launchd はキャッシュした旧定義を使います。`kickstart` は reload ではありません。この repo 自身も [bootout + bootstrap が必要だった事故](/Users/tomtim/Infra/mobile-work/rc-backend/tools/deploy-to-edith.sh:29) を記録しています。

したがって `ok` は「disk一致・job登録済・有効定義は未確認」と書くのが正確です。根本修正は、deploy が canonical plist を配置し、変更時に `bootout` + `bootstrap` すること。存在確認やログ書込可能性は別の起動前検査、実動作は health/last-run 検査に分けるべきです。

1. `launchctl list` の問題は第3列ではなく domain です  
現行 man page 上、第3列は Label で、停止中の定期 job も PID `-` で残ります。ただし SSH セッションの暗黙 domain と `~/Library/LaunchAgents` の GUI domain は同一とは限りません。後者はログインユーザー向けです。[Apple Support](https://support.apple.com/guide/terminal/script-management-with-launchd-apdc6c1077b-5d5d-4d35-9c19-60f2397b2369/mac)

[現在の `list | awk`](/Users/tomtim/Infra/mobile-work/rc-backend/tools/fleet-plist-parity-check.sh:62) はやめ、既存の [delivery-check と同じ `launchctl print gui/$uid/$label`](/Users/tomtim/Infra/mobile-work/rc-backend/tools/delivery-check.sh:43) にすべきです。加えて現在の pipeline は `launchctl list` が失敗しても `awk` が 0 を返し、全件を「NOT loaded」にする false red があります。

2. 「file一致 + loaded」は有効中の定義一致ではありません  
plist 編集後に reload されていなければ、launchd はキャッシュした旧定義を使います。`kickstart` は reload ではありません。この repo 自身も [bootout + bootstrap が必要だった事故](/Users/tomtim/Infra/mobile-work/rc-backend/tools/deploy-to-edith.sh:29) を記録しています。

したがって `ok` は「disk一致・job登録済・有効定義は未確認」と書くのが正確です。根本修正は、deploy が canonical plist を配置し、変更時に `bootout` + `bootstrap` すること。存在確認やログ書込可能性は別の起動前検査、実動作は health/last-run 検査に分けるべきです。

3. `TEMPLATE_ONLY` の全除外は false green です  
この example の可変部分は実質 [ProgramArguments のパス](/Users/tomtim/Infra/mobile-work/rc-backend/tools/com.fleet.rc-health-observer.plist.example:40) です。Friday 用期待値を生成して比較するのが最善です。難しければ、同じキーだけでなく Label、interval、全固定値、許可された実行パスを比較してください。`-- not compared` は説明であって検査ではありません。

MD5 を parsed-value 比較へ置き換えるのは反対です。raw hash を配布物一致、正規化した plist を意味的一致として併記すれば、コメントだけの差を「byte-only drift」と分類できます。コメント差も今回のような配布漏れの証拠なので、消すべきではありません。

なお [C3 が missing plist を rc=2 と期待](/Users/tomtim/Infra/mobile-work/rc-backend/test/fleet-plist-parity-controls.sh:94) していますが、不在は測定不能ではなく確定した parity failure、つまり rc=1 です。rc=2 は SSH・md5・解析自体が成立しない場合だけに限定してください。制御テストは12/12通過しましたが、この誤った契約を固定しています。
