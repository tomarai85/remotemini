Attack this. A change to a log-size cap that runs hourly, unattended, from a user LaunchAgent on a production Mac mini. Be brief — the two or three things actually wrong, not a survey.

## The change

`log-cap-all.sh` used to sweep exactly one directory: `~/Library/Logs/rc-backend`. It now takes any number of directories, and the plist passes two: that one plus `~/.rc-backend`.

**Why the second directory, since it holds the smaller files.** The cap exists to bound *runaway*, not size. The runaway this project actually walked up to (recorded as H-4) was: deploying a health-observer script without one of its dependencies turns a once-a-day false alert into a **10-minute loop** — and every line of that loop lands in `~/.rc-backend/health-observer.log`, which the sweep did not see. The cap had been placed where the big files are, not where the runaway would be. Measured on the host: `health-observer.log` 131,982 B (appended every 600 s), `digest-notify.log` 89,500 B (every 150 s). Small, and that is not the argument.

## Argument parsing (the part I most want attacked)

```bash
CAP=5242880
args=("$@")
n=${#args[@]}
if [ "$n" -gt 0 ]; then
    last="${args[$((n-1))]}"
    case "$last" in
        ''|*[!0-9]*) ;;                 # not numeric -> a directory
        *) CAP="$last"; unset 'args[n-1]' ;;
    esac
fi
for a in ${args+"${args[@]}"}; do DIRS+=("$a"); done
[ ${#DIRS[@]} -eq 0 ] && DIRS=("$HOME/Library/Logs/rc-backend")
```

The point of "trailing argument is the cap only if it is purely numeric" is that the previous call form `log-cap-all.sh <dir> <bytes>` keeps working unchanged, so the existing plist invocation and the existing control suite stay green while directories can be added without a new flag. Known limitation, accepted: a directory literally named `12345` cannot be passed.

## Fail-open I also closed

The old code did `[ -d "$DIR" ] || { echo ...; exit 0; }`. A one-character typo in a directory argument therefore reported success, and the LaunchAgent repeated that same lie every hour. Now a missing directory is counted and the script exits 2 (measurement not established). Exit codes: 0 = all within cap, 1 = one or more files failed, 2 = not measurable (missing directory, or zero files seen).

## What each file gets (unchanged from the earlier review you already did)

Per file over the cap: tail snapshot to `<file>.tail`, one `: > "$F"`, then one `>>` note saying where the history went. Glob stays `*.log` so `.tail` cannot match. `*.error.log` is deliberately not exempt.

## Attack these specifically

1. **`unset 'args[n-1]'` leaves a sparse array**, and I iterate with `${args+"${args[@]}"}`. Is that actually safe under `set -u` in bash 3.2 (the macOS system bash this LaunchAgent will use — `/bin/bash`), or am I relying on behaviour that differs between 3.2 and 5.x? The plist calls `/bin/bash` explicitly.

2. **Exit 2 on a missing directory, from a LaunchAgent.** Closing the fail-open means the job now exits non-zero whenever any listed directory is absent. `~/.rc-backend` is created by the backend at startup — so on a freshly booted box where the backend has not yet run, this job will fail hourly until it does. Is that the right trade, or have I converted a silent lie into recurring noise that will itself be ignored? What is the correct third state here?

3. **Two directories, one cap.** `~/Library/Logs/rc-backend` holds a 1.1 MB request log; `~/.rc-backend` holds a 130 KB observer log and also **non-log state files** (`health-state.json`, `*.mark`, `api.key`). The glob is `*.log` so those are not touched — but is sweeping a *state* directory with a truncating tool a bad idea on principle, regardless of the glob? Would a narrower target (naming the two log files) be safer than a directory sweep here, given that the directory's other contents are the thing the system's correctness depends on?

4. Anything else about running this hourly and unattended against a live production host that I am underweighting.

1. `unset` は安全

`/bin/bash` 3.2.57で「引数なし／CAPだけ／複数dir＋CAP／空白入りdir」を実測し、`set -u`でも正常でした。疎配列は仕様上許され、 `"${args[@]}"` は存在する要素だけを展開します。`${args+"${args[@]}"}` も、全要素を外した場合のnounset回避として機能しています。[GNU Bash Arrays](https://www.gnu.org/s/bash/manual/html_node/Arrays.html)

ここは直さなくてよいです。既存controlも16/16で通過しました。

2. exit 2より、状態遷移を監視していないことが問題

このplistでは非ゼロ終了は通知になりません。毎時実行され、結果がログと`LastExitStatus`に残るだけです。[Apple launchd.plist](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5)

正解は、インストール時に両ディレクトリを作ってからLaunchAgentをロードし、「missing＝常に異常」にすることです。起動順による未作成を許すなら、

- readiness前: `not-ready`
- readiness後に消失: exit 2
- 通知: 毎時ではなく、失敗への遷移または最終成功時刻のstaleで1回

に分けるべきです。現状のエラー出力がstdoutなのも弱く、非ゼロ診断はstderrへ出すべきです。
