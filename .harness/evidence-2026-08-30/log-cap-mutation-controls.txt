log-size-cap.sh — 実測と変異対照  (2026-08-30)
================================================================================
測った物: 「上限内に収まるか」ではなく **「収める過程で行を失わないか」**。
理由: 初版の検査は「大きさが増え続けるか」だけを見ていた。それは上書きが起きていても
      成立するので、**壊れ方を測れていなかった**(Codex に指摘されて気付いた)。

--------------------------------------------------------------------------------
1. 設計が2回変わった経緯(どちらも実測 / 外部の指摘で)
--------------------------------------------------------------------------------
(a) mv 回転 → 不採用。追記者は file を開いたままなので fd が古い inode に残る。
    実測: mv 後の新 file 0 B / 旧 inode 7,488,895 B(新しい方に1行も来ない)。

(b) tail を同じ file へ書き戻す(`cat "$tmp" > "$F"`)→ 不採用。
    offset 0 から書くので、書いている最中に追記された行を後続の write が上書きする。
    ★私の「fd が生きている」の実測は **追記が続く事** しか示しておらず、
      **行が失われない事は測っていなかった**。

(c) 採用 = 末尾を別 file へ退避 → `: > "$F"` を1回 → 何処へ消えたかを `>>` で1行。
    `>>` は O_APPEND なので常に EOF に書き、追記者の行を上書きしない。

--------------------------------------------------------------------------------
2. 検出器(何を数えているか)
--------------------------------------------------------------------------------
書き手が `SEQ-1`, `SEQ-2`, … を追記し続けている最中に切る。切った後の本体を読み、
  - 連番の **欠け**(b[i] != b[i-1]+1 の箇所数)
  - 途中で千切れた行の本数
を数える。

★最初に書いた検出器は「連番が **戻った** 箇所」を数えていて、変異対照が **緑のまま通った**。
  上書きは「順序が戻る」ではなく **「行が消える」** なので、逆行では捕まらない。
  検出器そのものを直した。

--------------------------------------------------------------------------------
3. 結果(Jervis)
--------------------------------------------------------------------------------
C. 本番版 · 同時追記中に上限 200000 B で切る
     本体 92,004 行 / 連番の欠け 0 箇所 / 壊れた行 0 本  → PASS

D. 変異対照 · `: > "$F"` を `cp "$snap" "$F"`(= Codex 前の形)に差し替え
     本体 103,998 行 / 連番の欠け 1 箇所 / 欠け例 (94000, 94002)  → 赤
     = SEQ-94001 は追記された後、書き戻しに上書きされて消えた。
     ★変異で赤くなる = この検査は本物(緑が「検査が無い」の意味ではない)。

--------------------------------------------------------------------------------
4. 結果(friday / athenas 実機)
--------------------------------------------------------------------------------
既定 5MB で本番 dir を掃く:
     log-cap-all: /Users/athenas/Library/Logs/rc-backend の 7 本を見て 0 本を切った
     (最大が rc-backend.log 1,147,825 B なので切らないのが正しい)

実機で切る所(本番 log ではなく /tmp の検体、同時追記あり):
     648,894 B -> 190 B(退避 106,117 B)
     本体 63,999 行 / 連番の欠け 0 箇所 / 切った後も追記継続: True  → PASS

LaunchAgent 据え付け:
     com.fleet.rc-log-cap  runs = 1 / last exit code = 0 / error log 空
     自分の log: 「9 本を見て 0 本を切った(上限 5242880 B)」

--------------------------------------------------------------------------------
5. 巨大1行の退行対照(以前ここで 81 バイト事故を出している)
--------------------------------------------------------------------------------
改行の無い 400KB の1行を上限 200000 B で切る:
     live=188 B / tail=100,117 B
     (`sed 1d` だけで処理していた初版はここで tail が 81 B に落ち、
      task の検査は「上限以下かつ 0 でない」しか見ないので PASS のまま通っていた)

--------------------------------------------------------------------------------
6. この上限が押さえられない物(正直に)
--------------------------------------------------------------------------------
悪意ある連打の即時。次の実行までの1時間に書けた量はそのまま乗るので、
実効の上限は「上限 + 1時間ぶん」。本当の止め方は配布口(OTA)側の認証か流量制限。

--------------------------------------------------------------------------------
7. 途中で見つけた別レーンの物(触っていない・報告のみ)
--------------------------------------------------------------------------------
`athenas:~/bin/rotate-cswap-log` が `tail -n 500 "$LOG" > "$TMP" && cat "$TMP" > "$LOG"`
= 上で不採用にした (b) と同じ形。単一の追記者で追記も稀なので実害は小さいが、
原理的には同じ取りこぼしをする。cswap レーンの持ち物なので変更していない。
