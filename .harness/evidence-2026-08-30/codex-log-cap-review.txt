Attack this. Two small shell scripts that will run unattended on a production Mac mini via launchd. Be brief — the two or three things actually wrong, not a survey.

## Why they exist
`rc-backend` (a Node server that injects keystrokes into a live tmux/Claude Code session) and its sibling jobs write logs to `~/Library/Logs/rc-backend/`. There is **no rotation of any kind**. One of the writers is an unauthenticated OTA file-distribution endpoint reachable on a tailnet — anyone on that tailnet can spam 404s, and each request writes a line.

Measured on the host today: `rc-backend.log` 1,034,264 B accumulated since a restart 4 days ago (~260 KB/day), `rc-phone-window.log` 470,708 B, `rc-ota.log` 431 B. Disk free 32 GiB. So this is **not** an imminent-overflow fix; it is a bound on abuse and runaway. Same disk also holds the desk's tmux transcripts.

`newsyslog` was the obvious answer and is out: its config lives in `/etc/newsyslog.d/`, which needs root. The service account has no sudo (structurally unavailable in this environment).

## Design choice I want attacked
**Truncate-keep-tail in place, NOT mv-rotation.** Reason: the writers hold the file open. `mv` leaves their fd on the old inode, so the new file gets nothing.

I measured this rather than assuming it:
```
writer appending in background; mv log log.rotated; : > log; wait 2s
new file: 0 B      old inode: 7,488,895 B
```
And the truncate path, same setup:
```
before cap: 68,490 B   right after cap: 68,718 B   2s later: 140,310 B
```
i.e. appends continued through the truncation.

## Script A — `log-size-cap.sh <file> [cap]` (default cap 5 MB)
```
size=$(stat -f%z "$F"); [ "$size" -le "$CAP" ] && exit 0
keep=$((CAP / 2))
tail -c "$keep" "$F" > "$tmp"
# drop the partial first line — UNLESS dropping it removes most of the content
head_dropped=$(sed '1d' "$tmp" | wc -c)
kept_all=$(wc -c < "$tmp")
if [ "$kept_all" -gt 0 ] && [ "$((head_dropped * 2))" -lt "$kept_all" ]; then
    body_cmd="cat"          # one very long line: keep it, note the truncated head
else
    body_cmd="sed 1d"
fi
{ printf '[log-size-cap] ... truncated before %s (cap %s B)%s\n' ...; $body_cmd "$tmp"; } > "$tmp2"
cat "$tmp2" > "$F"          # same inode on purpose
after=$(stat -f%z "$F"); [ "$after" -le "$CAP" ] || exit 1
```
That `head_dropped` branch exists because I shipped it without it first: the task's own verifier only asserted `size <= cap && size > 0`, so when a test fixture was one enormous base64 line, `sed 1d` cut 500 KB down to **81 bytes** and the verifier still said PASS.

## Script B — `log-cap-all.sh [dir] [cap]`
Globs `"$DIR"/*.log`, calls A on each, prints `saw N, capped M`, and exits 2 if N is 0 (a zero-file sweep must not read as "all within cap"). It globs the directory rather than listing filenames in a plist, because a hand-maintained list is how a thing silently stops covering a new file.

Intended to run from a user LaunchAgent (`StartInterval`, probably hourly).

## Attack these specifically
1. **The truncate window.** Between `tail -c` and `cat > "$F"`, a writer can append. Those bytes are lost, and worse — a writer using `O_APPEND` keeps a file offset that is now past EOF, so after truncation the next write may leave a hole (sparse NULs) or land at a stale offset. Does that actually happen on macOS/APFS with `O_APPEND` writers? Is the resulting file corrupt in a way that matters for a log?
2. **Is `cat > "$F"` even the right primitive?** Should this be `truncate`+seek, or open/`ftruncate`, or is shell the wrong tool entirely for a file with live appenders?
3. **`keep = CAP/2` means the file sawtooths** between CAP/2 and CAP. Over-frequent capping loses history; too-rare risks the bound. With ~260 KB/day and a 5 MB cap, is hourly sane or wasteful?
4. **Script B globs `*.log` but the writers also produce `*.error.log`** — those match the glob too. Any reason to treat error logs differently (they are near-empty now, but they are the ones you actually want history for)?
5. Anything about **running this unattended against files a live production server is writing** that I am underweighting. If the honest answer is "this whole approach is wrong, wait for a real logging library", say that.

Three real problems:

1. **`O_APPEND` will not create stale-offset holes, but `cat > "$F"` is still unsafe.** On macOS, a true `O_APPEND` writer relocates to EOF before every write, so truncation does not leave its next write at the old offset. A non-append writer can create a zero-filled hole because `ftruncate()` does not reset file offsets. [Apple `open(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/open.2.html), [POSIX `write()`](https://pubs.opengroup.org/onlinepubs/9699919799/functions/write.html), [POSIX `ftruncate()`](https://pubs.opengroup.org/onlinepubs/9699919799/functions/ftruncate.html)

   The worse race is that `cat` writes from offset 0 without append mode. A live appender can write between `cat`’s chunks, then a later `cat` write can overwrite that new log line. Lost or partial lines are possible. `truncate`+seek or a small C helper does not solve this without writer cooperation.

2. **Hourly is cheap, but it is not an abuse bound.** At 260 KB/day, after cutting to 2.5 MB it takes roughly 9.6 days to reach 5 MB again; hourly checks do not cause extra capping and cost essentially nothing. But under spam, the actual bound is approximately:

   `5 MB + bytes writable during the next hour`

   So hourly is fine for ordinary runaway detection, not hostile-rate containment. Authentication/rate limiting at the OTA endpoint, or writer-owned rotation/reopen, is the real control.

3. **For an interim solution, do not copy the tail back into the live file.** Save one bounded tail snapshot to another filename, then perform a single `: > "$F"`. That remains lossy between snapshot and truncate, but avoids `cat` overwriting concurrent appends. The correct long-term solution is for every writer to close/reopen during rotation, or use a logging library with size-based rotation.

`*.error.log` already matches `*.log`. Keep error logs bounded too; optionally give them a larger explicit cap because they have higher diagnostic value, but do not exempt them—an error storm is exactly when they become dangerous.
