# issue-driven -- 本質を捉えるスキル

安宅和人「イシューからはじめよ」に基づく、本質を捉えるための思考支援スキル。
ユーザーが持ちかけた課題・アイデア・計画に対して、表面ではなく本質のイシューを炙り出す。

Codex 版では `/issue-driven` のようなコマンド名は読み替えであり、ユーザーがこのスキル名を指定するか、「本質を見極めたい」「イシューを整理したい」と依頼した時に使う。

## 基本公式

```
バリュー = イシュー度 x 解の質
```

- イシュー度: 今この局面で、この問題に答えを出す必要性の高さ
- 解の質: そのイシューに対して、どこまで明確に答えを出せているか

**順序が全て。** イシュー度を先に上げ、その後に解の質を磨く。逆にすると犬の道（大量の作業で勝負する無駄な道）に陥る。

## 補完関係

- `/issue-driven`: イシューの質を上げる（問題設定）
- `/visionary-council`: 解の質を評価する（ソリューション評価）

この2つは対になる。issue-drivenでイシューを確定した後、visionary-councilでソリューション案を評価するのが理想的な流れ。

## モード一覧

| モード | コマンド例 | 動作 |
|---|---|---|
| デフォルト | `/issue-driven [入力]` | 入力タイプに応じてStep 0-4を実行 |
| クイック | `/issue-driven --quick [入力]` | Step 1のみ（3条件 + 犬の道チェック） |
| 深掘り | `/issue-driven --deep [入力]` | Step 1を対話形式で深掘り |
| 点検 | `/issue-driven --check [ファイルパス]` | 既存の計画・分析のイシュー度を診断 |

## 実行フロー

### 入口ルーティング（自動判定）

スキル起動時、ユーザー入力を以下の4タイプに自動分類し、適切なStepにルーティングする。

| タイプ | 判定基準 | 開始Step |
|---|---|---|
| A: 明確な課題 | 「Xが問題」「Xを解決したい」「Xを改善したい」 | Step 1 |
| B: 漠然とした欲求 | 「Xしたい」「何がいいか分からない」「方向性を決めたい」 | Step 0 |
| C: 既存分析あり | ファイルパス添付、既に構造化された計画・分析がある | Step 1（検証モード） |
| D: 技術課題 | CI/CD、パフォーマンス、リファクタ、バグ等の技術的問題 | Step 1（技術フレーム） |

判定に迷った場合はタイプAとして扱う。

**入力が空の場合**: ユーザーに「何について本質を見極めたいか？」と問いかけ、回答を待ってからルーティングする。

### --check モード（タイプC）の動作

`/issue-driven --check [ファイルパス]` で起動した場合:
1. 指定ファイルを読み込む
2. ファイル内容からイシューと仮説を抽出
3. Step 1の全チェック（3条件、犬の道、一次情報）を適用
4. 「このプランのイシュー度」を診断結果として出力
5. イシュー度が低い部分を指摘し、改善案を提示

## Step 0: プレイシュー（タイプBのみ）

イシューが存在しない状態から、イシューの種を見つける。

### 実行手順

1. **欲求の特定**
   ユーザーに問いかける: 「何を得たいか」ではなく「何が満たされていないか」
   - 収入 / 成長 / 自由 / 承認 / 知的刺激 / 社会貢献 / 安定
   - 文脈自動読み込みでプロジェクト情報があれば、それも参照する

2. **制約の整理**
   - 時間（1日何時間使えるか）
   - スキル（何ができるか、何ができないか）
   - リソース（資金、人脈、ツール）
   - リスク許容度（失敗しても大丈夫か）

3. **仮イシュー候補の生成**
   欲求と制約から、「○○は××ではないか」の形で仮イシューを3つ生成する。
   各候補に「なぜこれがイシューになりうるか」の1行説明を付ける。

4. **ユーザーの選択**
   「この中で最も"そうかもしれない"と感じるのはどれか？」と問い、選択されたものをStep 1に渡す。

## Step 1: イシューの見極め（核心）

**本質を捉える**ための最重要ステップ。全てのモードでこのStepを通る。

### 1a. 空・雨・傘による分離

ユーザーの入力を3層に分解する:

| 層 | 意味 | 問い |
|---|---|---|
| 空（事実） | 客観的に何が起きているか | 「何が見えるか？」 |
| 雨（解釈） | それはどういう意味か | 「それはつまり？」 |
| 傘（判断） | だから何をすべきか | 「だからどうする？」 |

**核心原則**: 多くの場合、ユーザーは「傘」（やりたいこと）を持ちかける。しかし本質は「空」と「雨」の間にある。事実の観察と解釈が不十分なまま判断に飛ぶと、的外れな行動になる。

分離の手順:
1. ユーザーの入力から「傘」（判断・行動）を特定する
2. その判断の前提となっている「空」（事実）を洗い出す
3. 事実と判断をつなぐ「雨」（解釈）を明示する
4. 解釈が飛躍していないか、別の解釈がありうるか検討する

### 1b. 仮説の言語化

イシューを仮説の形にする。

**言語化ルール:**
- 必ず **主語 + 述語 + スタンス（立場）** を含める
- スタンスを取ることで初めて検証可能になる

| 品質 | 例 | 問題点 |
|---|---|---|
| NG | 「市場規模はどうか？」 | ただの問い。スタンスがない。検証しようがない |
| NG | 「採用が難しい」 | 事実の記述。仮説ではない |
| OK | 「RPO市場は、AI導入で2年以内に構造転換するのではないか」 | スタンスがある。検証可能 |
| OK | 「"応募が来ない"の本質は、求人原稿の質ではなく、ターゲット企業の選定ミスではないか」 | 本質に迫る仮説 |

ユーザーの入力が「問い」の形なら、スタンスを取った仮説に変換して提示する。

### 1c. イシュー度の検証（3条件）

| 条件 | 問い | 合格 | 不合格 |
|---|---|---|---|
| **本質的な選択肢がある** | この問いに答えが出ると、方向性が変わるか？ | 答え次第でやることが根本的に変わる | 答えが出ても「ふーん」で終わる |
| **深い仮説がある** | 「なるほど」と膝を打つ直感があるか？ | 常識を覆す、意外性がある | 誰でも思いつく、当たり前すぎる |
| **答えを出せる** | 今の手段で検証できるか？ | データ収集・実験・ヒアリングで確認可能 | 必要なデータも手段も存在しない |

**3条件すべてを満たす必要がある。** 1つでも不合格なら、イシューの筋が悪い。

筋が悪い場合の対処:
- 本質的選択肢がない → イシューの粒度を上げる（より具体的に）
- 深い仮説がない → 一次情報に触れる、専門家の意見を聞く
- 答えを出せない → イシューを分解し、答えが出せるサブイシューに落とす

### 1d. 犬の道チェック

以下のパターンを検出したら警告を出す:

| パターン | ユーザーの言動 | 警告メッセージ |
|---|---|---|
| **ソリューション先行** | 「とにかく作ってみよう」「まず実装しよう」 | イシュー度が確定する前のソリューション着手は犬の道。方向転換時に全てが無駄になる |
| **網羅症** | 「全部やらなきゃ」「漏れがないように」 | 本当にやるべきことは100のうち1-2個。100を100のまま抱えるのは見極めの放棄 |
| **情報収集依存** | 「もっとデータを集めよう」「調査してからにしたい」 | 知り過ぎ注意。情報を集めすぎると仮説の自由度が死ぬ。今ある情報でスタンスを取れ |
| **労働量の自己正当化** | 「忙しいから仕方ない」「頑張っているから大丈夫」 | 作業量はバリューの指標ではない。イシュー度が低い仕事を大量にやっても価値はゼロ |
| **完璧主義** | 「もっと精度を上げてから」「まだ不完全だから」 | 60%ルール。完璧を目指さず高速回転させ、サイクルで深める |

### 1e. 一次情報チェック

ユーザーの判断が何に基づいているかを確認する。

- **一次情報**: 誰のフィルターも通っていない生のデータ（直接の観察、インタビュー、生ログ、自分の体験）
- **二次情報**: 他人がまとめたもの（記事、レポート、まとめサイト、人から聞いた話）

チェック項目:
- 「その判断は一次情報に基づいているか？」
- 「二次情報だけで判断していないか？」
- 「一次情報を取りに行く手段はあるか？」

一次情報が不足している場合: Step 4のアクションに「一次情報を取得する」を含める。

### 技術課題向けの調整（タイプD）

技術課題ではフレームワークの一部を読み替える:

| 標準フレーム | 技術課題での読み替え |
|---|---|
| 表面 vs 本質 | 症状 vs 原因 |
| 犬の道 | 根本原因を特定せずにパッチを当て続けること |
| 本質的選択肢 | 技術的選択肢（アーキテクチャ判断が変わるか） |
| 一次情報 | 実測データ（プロファイリング、ログ、メトリクス） |
| 仮説の言語化 | 「○○が遅い原因は、××がボトルネックではないか」 |

## Step 2: イシューの分解

Step 1で確定したイシューを、検証可能な単位に分解する。

### 2a. サブイシューへのMECE分解

メインイシューを「漏れなく・ダブりなく」3-5個のサブイシューに分解する。

- 仮説を立てる（主語+述語+スタンス）

### 2b. 絵コンテ（分析設計）

各サブイシューについて、分析に入る前に「何と何を比較すれば検証できるか」を設計する。

各サブイシューに対して以下を定義:
- **比較対象**: 何を比較するか
- **ベンチマーク**: 何と比較するか
- **評価軸**: どんな基準で判断するか
- **十分条件**: どんな結果が出れば「仮説が支持された」と言えるか

データを集める前にこの設計を済ませる。設計なきデータ収集は犬の道の入口。

### 2c. ストーリーラインの型選択

分解したサブイシューをどう組み立てるか、2つの型から選ぶ:

**WHYの並び立て（論証型）:**
「なぜXなのか？ 理由1、理由2、理由3」
- 結論が先にあり、根拠を並列に示す
- 論理的な説得に向く

**空・雨・傘（説得型）:**
「事実→解釈→判断」
- ストーリーとして流れがある
- 相手の理解を段階的に積み上げるのに向く

選択基準:
- 結論に自信がある → WHYの並び立て
- 相手を段階的に説得したい → 空・雨・傘
- 複数の解釈がありうる → 空・雨・傘（解釈の段階で分岐を示せる）

## Step 3: 本質の検証

分解した各サブイシューに対して品質チェックを適用する。

### 3a. So What?テスト

各サブイシューの仮説に「だから何？」を問う:

- 「この仮説が正しいとして、何が変わるか？」
- 「受け手にとってどんな意味があるか？」
- **何も変わらないなら、そのサブイシューは本質ではない → 削る**

So What?テストを通過しないサブイシューは、いくら論理的に正しくても価値がない。勇気を持って削る。

### 3b. 右脳と左脳の往復

データ分析（左脳）の結果に対して、直感（右脳）で検証する:

- 「数字はこう言っているが、何かおかしくないか？」
- 「この結論は、自分の実体験と矛盾していないか？」
- 「同じデータから逆の結論を導くことはできないか？」

違和感があれば、その違和感を言語化し、仮説を修正する。数字だけで結論を出さない。

## Step 4: アクション

### 4a. 検証方法を3つに絞る

Step 2-3の結果から、最もイシュー度の高いサブイシューに対する検証方法を **3つだけ** 選ぶ。

**絞る基準（優先順）:**
1. イシュー度が最も高い（答えが出ると方向性が変わる）
2. 検証コストが最も低い（60%ルール: 完璧を目指さず高速回転）
3. 一次情報を取得できる（二次情報の分析より、一次情報の取得を優先）

### 4b. 出力の分離

アクションを2種類に明確に分ける:

- **Codexで今すぐ支援できるもの**: ヒアリングシート作成、検証マトリクス生成、競合分析、データ整理、タスクリスト作成、プロトタイプのコード等
- **ユーザー自身が動く必要があるもの**: 対面ヒアリング、関係構築、意思決定、交渉、実地調査等

技術課題（タイプD）の場合は追加で:
- **実装への橋渡し**: 具体的なコード変更提案、設定ファイルの修正案、アーキテクチャ図等

### 4c. 捨てるものの明示

「今やること」と等しい重みで「今やらないこと」を明示する。捨てる理由を付けることで、優先順位の判断を透明にする。

## --deep モード（対話的深掘り）

安宅和人の思考法をシミュレートし、ユーザーと対話しながら本質を炙り出す。

### 動作

**入力テキストがある場合:**
1. Step 1a（空・雨・傘）の結果を提示
2. 仮説を提示し、ユーザーに「これは本質か？」と問う
3. ユーザーの反応に対して切り返し、より深い本質を探る
4. 合意に達するまで対話を繰り返す
5. 合意後、Step 1c-1eのチェックを実行して出力

**入力テキストがない場合:**
1. 「何について深掘りしたいか？」と問いかける
2. ユーザーの回答を受けて上記フローを開始する

### 反論パターン

対話では以下の型で切り返す。

- 表面に留まる場合: 顧客要望、データ、業界常識を「空」として扱い、その裏の構造と別解釈を問う。
- 犬の道に向かう場合: 早期実装、網羅症、過剰調査を止め、最も方向性が変わる1つの問いに戻す。
- 諦めに向かう場合: 感情ではなく制約を分解し、「今は不可能」と「根本的に不可能」を分ける。

# Workflow Principles

## Current-state confirmation
When asked for a fix, do not execute immediately. First inspect the current state, propose, get approval, then execute.

## Task planning
- Tasks with 3+ steps or design decisions: plan via Plan mode before starting
- Write the plan in `~/.claude/tasks/todo.md` as a checklist
- On any problem, stop and re-plan immediately (do not push through)

## Plan Mode Enumeration Checklist
Before calling ExitPlanMode, walk through the 10 items below.
Ask all ambiguous items via AskUserQuestion inside Plan mode.
Do not surface additional confirmations after entering implementation phase
(if one leaks out, recognize it as a failure of upfront enumeration).

1. Tech / library choice
2. Architecture approach
3. UX / design preferences
4. Scope boundary (how far to go)
5. Intrusion scope into existing code / environment
6. Edge case handling policy
7. Error behavior
8. Completion criteria
9. Deploy / delivery target
10. Conflicts with existing settings / rules

Contract: Plan mode is the batch confirmation phase. Missed questions here destroy the value of autonomous execution. No shortcuts on this checklist.

- On noticing a hacky fix, self-question "is there a deeper solution?" before proceeding
- Skip for trivially obvious simple fixes

tailscale serve --bg --https=9443 http://127.0.0.1:8787
  → Available within your tailnet:
     https://desk.tailnet.example:9443/
```

実測で確かめた性質(2026-08-25、Codex 追認):

1. 任意の HTTPS ポートで serve は張れる。**443/8443/10000 の制限は Funnel の話であって
   serve の話ではない**
2. **Funnel が使えるのはその3ポートだけ**。9443 を選ぶ事で「うっかり公開する」が
   構造的に起こせなくなる(現行 Tailscale が強制する性質であって、将来の保証ではない)
3. 追加は**加算的**で 443 の設定を壊さない(前後の JSON を保存して確認)
4. ★`tailscale serve reset` は**使わない**。共有設定を全部消すので resonance-os を巻き込む。
   撤去は `serve` の `https=9443` 旗を off で**ポート単位**に行う

# app-usage-census.sh — 電話(client=app)からの要求を**日ごとに数えて積む**。
#
# ── なぜ要るか(2026-08-30)──────────────────────────────────────────────────
# CONTINUITY の H-3 は OPEN で、解除条件が「合成の通知を送らずに 3〜7 日の起きている時間に
# 本物の機会が来た時、Tom がアプリ経由で動くか観測する」。その観測の手立ては
# **人が思い出して grep する**事だけだった —— 木を全部 grep しても `client=app` を
# **読む道具は1つも無い**(書き手 `src/reqlog.mjs` と其の検査だけ)。
#
# ★同じ日に据えた上限が、その観測窓を消しに来る。`rc-backend.log` は約 260KB/日で伸び、
#   5MB に当たるのは2週間ほど先。切ると末尾の半分だけが `<file>.tail` に残り、
#   **次に切った時に其の退避も上書きされる**(1世代しか持たない)。
#   つまり「数え終わる前に、数える元が消える」。
#
# だから**上限の外**へ、日ごとの数だけを積む。生の行は運ばない(要らないし、
# 運べば同じ大きさの問題を別の場所に作るだけ)。
#
# ★積み方は**日ごとの max**。和ではない。
#   log は切られるので、切った後の走行では過去の日の数が**減って**見える。
#   和にすると二重に数え、上書きにすると減る。max なら
#   「一度観測した数より下がらない」= 窓が消えても記録が残る。
#   同じ日に本当に増えた時も max で伸びる。
#
# 使い方:
#   bash rc-backend/tools/app-usage-census.sh
#   RC_CENSUS_LOG=<log> RC_CENSUS_OUT=<tsv> bash …     # 検査の継ぎ目
#
# 出力: `<date>\t<count>` の TSV(日付順)。既定の置き場は **上限を掛けている dir の外**。
#
# 終了コード: 0=積んだ / 1=書けない / 2=元 log が無い(測定不成立。0 に丸めない)
set -uo pipefail

LOG="${RC_CENSUS_LOG:-$HOME/Library/Logs/rc-backend/rc-backend.log}"
# ★置き場は `~/Library/Logs/rc-backend` でも `~/.rc-backend` でもない ——
#   どちらも `com.fleet.rc-log-cap` が掃く。掃かれる場所に「掃かれると困る物」を置かない。
OUT="${RC_CENSUS_OUT:-$HOME/rc-census/app-usage.tsv}"
# ★時刻と版まで分けた副台帳(2026-08-30)。日次の合計だけだと H-3 の解除条件
# (「**起きている時間**に本物の機会が来た時、Tom がアプリ経由で動くか」)を後から評価できない ——
#   1日 100 件が深夜の常駐なのか昼の実使用なのかが、合計からは復元できない。
#   `build` も併せて持つ: 版が変わった前後で使い方が変わったかは、版を捨てた台帳では問えない。
# ★**日次の合計は形を変えない**。既に 4 日ぶん積んであり、形を変えると其の履歴が読めなくなる。
#   足すのは別 file。壊さずに増やす。
DETAIL_OUT="${RC_CENSUS_DETAIL_OUT:-${OUT%.tsv}-detail.tsv}"

if [ ! -f "$LOG" ]; then

# ★`client=app` を**語として**当てる。`client=apple` の様な将来の語に巻き込まれない為。

    END { for (k in n) printf "%s\t%d\n", k, n[k] }

# ★`build=` が無い行(2026-08-30 より前の机)は `-` として数える。捨てない ——

            else if ($i ~ /^build=/) { b = substr($i, 7) }

        if (d != "" && h != "") n[d "\t" h "\t" b]++
    }
    END { for (k in n) printf "%s\t%d\n", k, n[k] }
' "$LOG" | sort > "$dtmp"

    awk -F'\t' '
        NR == FNR { if (NF >= 4) old[$1 "\t" $2 "\t" $3] = $4 + 0; next }
        { k = $1 "\t" $2 "\t" $3; cur = $4 + 0

        END { for (k in old) if (!(k in seen)) printf "%s\t%d\n", k, old[k] }
    ' "$DETAIL_OUT" "$dtmp" | sort > "$dtmp.new"
else
    cp "$dtmp" "$dtmp.new"
fi
mv -f "$dtmp.new" "$DETAIL_OUT" || { echo "app-usage-census: 副台帳を書けない: $DETAIL_OUT" >&2; /bin/rm -f "$dtmp"; exit 1; }
/bin/rm -f "$dtmp"
days="$(wc -l < "$OUT" | tr -d ' ')"
total="$(awk -F'\t' '{s += $2} END {print s + 0}' "$OUT")"
drows="$(wc -l < "$DETAIL_OUT" 2>/dev/null | tr -d ' ')"
echo "app-usage-census: $days 日 / 述べ $total 件を $OUT に積んだ(時刻×版 $drows 行 = $DETAIL_OUT)"
exit 0

The backend writes one line per request; a `client=` field classifies the caller (`app`/`tool`/`probe`/`none`), and as of today a `build=` field carries the app's build number, parsed from the product User-Agent (raw UA is never logged, by standing rule).

An open hypothesis, H-3, asks: **does the owner actually use this app?** Its stated discharge condition is to observe, over 3-7 waking days and without sending a synthetic notification, whether he acts through it. The recorded premise was: `client=app` rows are his real phone, because simulator builds lack the baked-in server URL and structurally cannot reach the desk.

An hourly job accumulates a per-day count of `client=app` requests into a file outside the log-rotation scope, so a size cap cannot eat the evidence. Day totals only.

## The change

A second file, same job, same accumulation rule: `date <TAB> hour <TAB> build <TAB> count`. Day totals are untouched (four days already accumulated; changing that shape would make the history unreadable). Both files use per-key max-merge rather than sum, because the source log gets truncated and a later run sees fewer rows for a day already counted.

## What it immediately showed, and why I am asking you

Real production data, first run:

```

2026-08-30  13時(CDT)  build=100   6
2026-08-30  15時(CDT)  build=1    12
2026-08-30  15時(CDT)  build=102  10

So `build=1` is **my own automated control runs reaching the real backend**.

That falsifies H-3's premise: `client=app` is not "the owner's phone". His own count for today is 36 of the 593 accumulated, not 593.

## Attack these

1. **Is `build` a sound discriminator, or did I just replace one wrong premise with another?** The owner's build number changes every time I publish (96 → 102 → 105). A rule like "app rows whose build equals the last published build are his" breaks the moment I publish while he is still on the old one — which is the normal state. What is the right way to separate his traffic from my harness's, using only per-request metadata that never includes a raw device identifier?

2. **The day totals are now known to be contaminated** — four accumulated days mixing his phone with my control runs, with no way to split them retroactively because the old rows have no build. 3. **max-merge on a per-hour key.** A day's rows can only grow. If the log is truncated mid-hour and the job runs, that hour's count is preserved — good. But if a genuinely *new* hour arrives with fewer requests than an old identical key... there is no collision, keys include the date. Is there a case where max-merge silently overstates?

4. Anything about accumulating a growing per-hour record outside the rotation scope that I am underweighting — it is unbounded by construction, one row per (day, hour, build).

# issue-driven -- 本質を捉えるスキル

安宅和人「イシューからはじめよ」に基づく、本質を捉えるための思考支援スキル。
ユーザーが持ちかけた課題・アイデア・計画に対して、表面ではなく本質のイシューを炙り出す。

Codex 版では `/issue-driven` のようなコマンド名は読み替えであり、ユーザーがこのスキル名を指定するか、「本質を見極めたい」「イシューを整理したい」と依頼した時に使う。

## 基本公式

```
バリュー = イシュー度 x 解の質
```

- イシュー度: 今この局面で、この問題に答えを出す必要性の高さ
- 解の質: そのイシューに対して、どこまで明確に答えを出せているか

**順序が全て。** イシュー度を先に上げ、その後に解の質を磨く。逆にすると犬の道（大量の作業で勝負する無駄な道）に陥る。

## 補完関係

- `/issue-driven`: イシューの質を上げる（問題設定）
- `/visionary-council`: 解の質を評価する（ソリューション評価）

この2つは対になる。issue-drivenでイシューを確定した後、visionary-councilでソリューション案を評価するのが理想的な流れ。

---

## モード一覧

| モード | コマンド例 | 動作 |
|---|---|---|
| デフォルト | `/issue-driven [入力]` | 入力タイプに応じてStep 0-4を実行 |
| クイック | `/issue-driven --quick [入力]` | Step 1のみ（3条件 + 犬の道チェック） |
| 深掘り | `/issue-driven --deep [入力]` | Step 1を対話形式で深掘り |
| 点検 | `/issue-driven --check [ファイルパス]` | 既存の計画・分析のイシュー度を診断 |

---

## 実行フロー

### 入口ルーティング（自動判定）

スキル起動時、ユーザー入力を以下の4タイプに自動分類し、適切なStepにルーティングする。

| タイプ | 判定基準 | 開始Step |
|---|---|---|
| A: 明確な課題 | 「Xが問題」「Xを解決したい」「Xを改善したい」 | Step 1 |
| B: 漠然とした欲求 | 「Xしたい」「何がいいか分からない」「方向性を決めたい」 | Step 0 |
| C: 既存分析あり | ファイルパス添付、既に構造化された計画・分析がある | Step 1（検証モード） |
| D: 技術課題 | CI/CD、パフォーマンス、リファクタ、バグ等の技術的問題 | Step 1（技術フレーム） |

判定に迷った場合はタイプAとして扱う。

**入力が空の場合**: ユーザーに「何について本質を見極めたいか？」と問いかけ、回答を待ってからルーティングする。

### --check モード（タイプC）の動作

`/issue-driven --check [ファイルパス]` で起動した場合:
1. 指定ファイルを読み込む
2. ファイル内容からイシューと仮説を抽出
3. Step 1の全チェック（3条件、犬の道、一次情報）を適用
4. 「このプランのイシュー度」を診断結果として出力
5. イシュー度が低い部分を指摘し、改善案を提示

---

## Step 0: プレイシュー（タイプBのみ）

イシューが存在しない状態から、イシューの種を見つける。

### 実行手順

1. **欲求の特定**
   ユーザーに問いかける: 「何を得たいか」ではなく「何が満たされていないか」
   - 収入 / 成長 / 自由 / 承認 / 知的刺激 / 社会貢献 / 安定
   - 文脈自動読み込みでプロジェクト情報があれば、それも参照する

2. **制約の整理**
   - 時間（1日何時間使えるか）
   - スキル（何ができるか、何ができないか）
   - リソース（資金、人脈、ツール）
   - リスク許容度（失敗しても大丈夫か）

3. **仮イシュー候補の生成**
   欲求と制約から、「○○は××ではないか」の形で仮イシューを3つ生成する。
   各候補に「なぜこれがイシューになりうるか」の1行説明を付ける。

4. **ユーザーの選択**
   「この中で最も"そうかもしれない"と感じるのはどれか？」と問い、選択されたものをStep 1に渡す。

/**
 * 会話に紐づく道。`:id` は伏せ、動作名だけ残す。
 *
 * ★**server.mjs の振り分けもこれを使う**(写しを持たない)。最初は各々が同じ正規表現を
 *   持つ形にしかけたが、それは此処で何度も踏んだ型 —— 道を1本足した時に片方だけが古くなり、
 *   ログは新しい道を `(other)` と書き続ける。しかも**ログが静かなだけ**なので誰も気づかない。
 *   一覧は1箇所に集める。置き場を此処にしたのは「パスの型」を決める責任が此処だから。
 */
// ★action は**白名簿**(2026-08-16 に title / archive / return-request を追加)。
// 追加を忘れると handler が在っても**到達不能**になる — 実際に其の状態で3本を
// 出荷しかけ、Codex の敵対レビューが掴んだ(静的検査は字面の存在しか見ないので素通り)。
// 検体 = test/title-route.test.mjs の「到達できる」検査(regex に当てて実測する)。
export const SESSION_ROUTE_RE = /^\/api\/sessions\/([^/]+)\/(history|messages|stream|poll|interrupt|status|choice|queue|title|archive|return-request|digest|attach)$/;

/**
 * 語彙 = 小文字で始まり、小文字/数字/ハイフン/下線だけ、24字まで。
 *
 * ★下線を許すのは飾りではない: 実物の理由は `cwd_unknown` / `cwd_missing` / `cwd_untrusted` /
 *   `spawn_failed`(trust.mjs / server.mjs)と `pane-gone` / `composer-mismatch`(blocked.mjs)が
 *   **綴りを分けて**混在している。下線を弾いた初版は、e2e の実物のログで
 *   `route=worker code=409 reason=-` を出した —— 拒否の理由が定数として在るのに欄が空、
 *   つまり**一番読みたい行だけが黙る**形。緩めても網は緩まない(空白も `:` も依然弾く)。
 *   出す時はハイフンに寄せる。ログの中で同じ物が2通りに綴られると grep が二度要る。
 */
const TOKEN = /^[a-z][a-z0-9_-]{0,23}$/;

/** 記録の置き場。`res` に生の名前で生やすと将来 node 側の property と衝突しうる。 */
export const LOG = Symbol("rc-reqlog");

/**
 * パスの**型**。表に在る物はそのまま、会話の道は `:id` に畳む、それ以外は `(other)`。
 * @param {string} path 生のパス(`?` より前)
 * @param {Set<string>} [known] 表に在るパス(server.mjs が配る表 + 固定の api から作る)
 */
export function pathShape(path, known) {
  if (known && known.has(path)) return path;
  const m = SESSION_ROUTE_RE.exec(path);
  if (m) return `/api/sessions/:id/${m[2]}`;
  return "(other)";
}

/** 会話の道なら sessionId の**先頭8文字**。それ以外は空。 */
export function sessionOf(path) {
  const m = SESSION_ROUTE_RE.exec(path);
  return m ? m[1].slice(0, 8) : "";
}

/** 語彙に当たれば返す(下線はハイフンに寄せる)。当たらなければ空(= 行では `-`)。 */
export function token(v) {
  if (typeof v !== "string") return "";
  const s = v.trim().toLowerCase();
  return TOKEN.test(s) ? s.replace(/_/g, "-") : "";
}

/**
 * `error` の**定数**だけを語彙へ寄せる。`bad body: <構文解析器の言い分>` の様に
 * 外来の文字が混じった物は `:` や `"` で弾かれて空になる —— それが正しい。
 * 40字を超える物も空。長い error は説明であって語彙ではない。
 */
export function errSlug(v) {
  if (typeof v !== "string" || v.length > 40) return "";
  if (!/^[A-Za-z0-9 _-]+$/.test(v)) return "";
  const s = v.trim().toLowerCase().replace(/[ _]+/g, "-");
  return TOKEN.test(s) ? s : "";
}

/** method も外から来る。表に在る形だけ出す。 */
function methodOf(m) {
  return /^[A-Z]{3,10}$/.test(String(m || "")) ? String(m) : "(other)";
}

/**
 * 枝が**自分で**名乗る。応答の中身から拾えない物(経路の判定が本文に出ない場合)と、
 * 拾わせたくない物(500 の生の例外文)の為に在る。先に名乗った方が勝つ。
 */
export function markResult(res, fields) {
  const st = res && res[LOG];
  if (!st || st.emitted || !fields) return;
  if (!st.route) st.route = token(fields.route);
  if (!st.reason) st.reason = token(fields.reason);
}

/**
 * `json()` から呼ぶ。本文の `route` / `reason` / `error` は**この repo の定数**なので
 * 語彙に当たる。当たらない物(自由文)は落ちて `-` になる = 中身が漏れない。
 */
export function noteBody(res, obj) {
  const st = res && res[LOG];
  if (!st || st.emitted || !obj || typeof obj !== "object") return;
  if (!st.route) st.route = token(obj.route);
  if (!st.reason) st.reason = token(obj.reason) || errSlug(obj.error);
}
