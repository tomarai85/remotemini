Attack this. A rate limiter added to an unauthenticated file-distribution endpoint running unattended on a production Mac mini. Be brief — the two or three things actually wrong, not a survey.

## What the endpoint is

`ota-server.mjs` serves an Ad Hoc iOS `.ipa` + `manifest.plist` + a landing page from `~/ota/<24-hex-secret>/`. It listens on `127.0.0.1:8788` only; the sole path in is `tailscale serve`, which proxies `https://friday.<tailnet>.ts.net:9443/ota -> http://127.0.0.1:8788` (tailnet-only, not Funnel). It **cannot carry authentication** — iOS `installd` sends no custom headers — so the secret path segment is the whole access control. Anyone on the owner's tailnet can hit it, and that tailnet still contains a machine that was given away.

Until now nothing bounded request volume. A log size cap was added earlier today, but that bounds the *trace* of abuse, not the abuse.

## The limiter

```js
const RATE_PER_MIN  = Number(process.env.OTA_RATE_PER_MIN || 120);
const RATE_WINDOW_MS = 60_000;
const RATE_MAX_PEERS = 2048;
const hits = new Map();            // peer -> number[] (timestamps)

function peerOf(req) {
    const xff = String(req.headers["x-forwarded-for"] || "");
    if (xff) {
        const hops = xff.split(",").map(h => h.trim()).filter(Boolean);
        if (hops.length) return { key: hops[hops.length - 1], src: "xff" };   // LAST hop
    }
    return { key: String(req.socket?.remoteAddress || "?"), src: "sock" };
}

function overRate(key, now) {
    let arr = hits.get(key);
    if (!arr) {
        if (hits.size >= RATE_MAX_PEERS) {
            const oldest = hits.keys().next().value;      // insertion order
            if (oldest !== undefined) hits.delete(oldest);
        }
        arr = []; hits.set(key, arr);
    }
    while (arr.length && now - arr[0] > RATE_WINDOW_MS) arr.shift();
    if (arr.length >= RATE_PER_MIN) return true;
    arr.push(now);
    return false;
}
```
The check runs **before** method dispatch and path resolution, so a flood does not buy the attacker a stat() per request. Over the limit: 429 + `Retry-After: 60`, and the request is still logged (`code=429`).

## What I measured rather than assumed

- The socket address is useless for identity: everything arrives from 127.0.0.1 through the proxy. Confirmed against the live config (`/ota -> http://127.0.0.1:8788`).
- So the log records **which source was used** — `peer=xff` or `peer=sock`, the source only, never the value (this log's standing rule is that no raw client identifier is written). Hitting the real tailnet URL logs `peer=xff`, so tailscale does forward the header.
- I first keyed on `hops[0]`. Rotating a client-supplied first hop then bypasses the limiter completely — measured, 20 requests with `X-Forwarded-For: 10.0.0.$i, 10.0.0.0` produced **0** 429s. Switching to the last hop gives 15/20. The mutation is kept as a control.
- The default 120/min never touches a real install: an install is landing page + manifest + ipa; three rounds of that (9 requests) sees no 429.

## Attack these specifically

1. **Is "last hop" actually safe here?** It rests on tailscale serve *appending* its own value to a client-supplied header rather than replacing or passing it through. I inferred that from `peer=xff` appearing plus general proxy convention — I did **not** verify what tailscale does with a client-supplied `X-Forwarded-For`, because my log deliberately does not record the value. Is there a way to establish this that does not involve logging a client-controlled string? And if tailscale *replaces* rather than appends, does last-hop still hold?

2. **`hits.keys().next().value` evicts in insertion order, not least-recently-used.** With 2048 slots and a peer set of ~5 real devices, is that exploitable — can a flooder from one tailnet address cycle enough distinct keys to evict a legitimate peer's window, and does that even matter given eviction only *resets* someone's count (fails open, never denies)?

3. **A sliding window of timestamps per peer.** The array is bounded at RATE_PER_MIN because the over-limit branch returns without pushing. Is there a case where it is not — and is a per-peer array of up to 120 numbers the right structure here versus a counter with a reset, given this process also streams a 2 MB file?

4. **429 during a genuine install on a bad network.** installd retries, and a large ranged download could in principle issue many requests. 120/min was chosen as "obviously above a real install" without measuring a retry storm. What would a real failing install look like, and is there a shape that keeps abuse bounded while making it structurally impossible to refuse the owner — for instance never rate-limiting the manifest/landing page, only the .ipa, or the reverse?

5. Anything about adding a limiter to the one path a person uses to recover their phone that I am underweighting. If the honest answer is "a rate limiter is the wrong control here and the real fix is X", say that.

        // ★**末尾**を取る。先頭ではない —— 客は自分で `X-Forwarded-For` を付けられるので、
        //   先頭を鍵にすると header を回すだけで限流を素通りできる(鍵が毎回変わる)。
        //   信頼できる代理が1段(此処は tailscale serve だけ)の時、**自分に一番近い側 =
        //   末尾**が其の代理の書いた値で、客には書き換えられない。
        //   ★**推測ではなく実測で確定**(2026-08-30)。本番の tailnet 経路へ、先頭 hop を
        //     130 通りに偽装しながら 130 回叩いた: **200 が 120 / 429 が 10** ——
        //     既定の上限 120/分ちょうどで断られた。もし代理が客の header を素通りさせて
        //     いれば鍵が毎回変わって 429 は 0 になる。つまり tailscale serve は
        //     **自分の値を追記**しており、末尾は客に書けない。
        //   ★此の測り方は header の**値を1度も記録しない**。行に残るのは `peer=xff` の
        //     1語だけで、判定は 429 が出るか否かという振る舞いで取っている。
        const hops = xff.split(",").map((h) => h.trim()).filter(Boolean);
        if (hops.length) return { key: hops[hops.length - 1], src: "xff" };
    }
    // 直に叩かれた時(= 127.0.0.1 に居るのは此の機体の中の誰か)。
    return { key: String(req.socket?.remoteAddress || "?"), src: "sock" };
}

function overRate(key, now) {
    let arr = hits.get(key);
    if (!arr) {
        // 相手が増え続けても地図が無限にならない様に、古い物から落とす。
        if (hits.size >= RATE_MAX_PEERS) {
            const oldest = hits.keys().next().value;
            if (oldest !== undefined) hits.delete(oldest);
        }
        arr = [];
        hits.set(key, arr);
    }
    // 窓の外を捨ててから数える(件数ではなく**時刻**を持つので、窓の境界で緩まない)。
    while (arr.length && now - arr[0] > RATE_WINDOW_MS) arr.shift();
    if (arr.length >= RATE_PER_MIN) return true;
    arr.push(now);
    return false;
}

結論: `last hop`、FIFO eviction、timestamp配列は主な問題ではありません。直すべきは次の3点です。

1. 根本のアクセス制御が違う

まず譲渡済み端末をtailnetから失効させ、secret pathもローテーションすべきです。TailscaleのACL/GrantはServeにも適用されます。また、`installd`がheaderを付けなくても、Serve自身がspoof済みheaderを除去して`Tailscale-User-Login`等を注入できます。[Tailscale Serve documentation](https://tailscale.com/docs/features/tailscale-serve#identity-headers)

ただし譲渡端末が同じユーザーidentityならheaderだけでは区別できません。端末失効、または許可端末のTailscale IPに限定したGrantが先です。rate limiterはその後の保険です。

2. limiterが要求数しか縛らず、実資源を縛っていない

120個の`.ipa` GETは、120個のsocketとfile streamを同時に開けます。[現在の5分timeout](/Users/tomtim/Infra/mobile-work/rc-backend/tools/ota-server.mjs:286)は絶対期限ではなくinactivity timeoutなので、少量ずつ読み続ければ維持できます。次の窓でさらに120個追加でき、`EMFILE`等でownerも巻き込めます。Nodeもsocket timeoutの既定・意味をそのように定義しています。[Node HTTP documentation](https://nodejs.org/api/http.html#servertimeout)

対策は「manifestだけ除外」ではありません。IPAが拒否されれば結局installできません。

- 非ownerの同時IPA転送数を小さく制限
- 非owner全体にもglobal concurrency cap
- 転送には絶対wall-clock期限
- owner identity/許可端末用の予約laneは429にしない

失敗installは、途中切断後のIPA再GETや`Range`再開という形になります。Appleが上限を契約しているわけではないため、120という推測よりowner laneで安全性を作る方が堅いです。

3. `RATE_PER_MIN`の検証漏れ

[`Number(...)`](/Users/tomtim/Infra/mobile-work/rc-backend/tools/ota-server.mjs:142)は`NaN`や`Infinity`を許します。その場合`arr.length >= RATE_PER_MIN`が永遠に成立せず、配列も無限に伸びます。起動時に「有限な正のsafe integer」でなければ落とすべきです。正常値ならtimestamp配列は120件に収まり、counterへ変える必要はありません。

結論: `last hop`、FIFO eviction、timestamp配列は主な問題ではありません。直すべきは次の3点です。

1. 根本のアクセス制御が違う

まず譲渡済み端末をtailnetから失効させ、secret pathもローテーションすべきです。TailscaleのACL/GrantはServeにも適用されます。また、`installd`がheaderを付けなくても、Serve自身がspoof済みheaderを除去して`Tailscale-User-Login`等を注入できます。[Tailscale Serve documentation](https://tailscale.com/docs/features/tailscale-serve#identity-headers)

ただし譲渡端末が同じユーザーidentityならheaderだけでは区別できません。端末失効、または許可端末のTailscale IPに限定したGrantが先です。rate limiterはその後の保険です。

2. limiterが要求数しか縛らず、実資源を縛っていない

120個の`.ipa` GETは、120個のsocketとfile streamを同時に開けます。[現在の5分timeout](/Users/tomtim/Infra/mobile-work/rc-backend/tools/ota-server.mjs:286)は絶対期限ではなくinactivity timeoutなので、少量ずつ読み続ければ維持できます。次の窓でさらに120個追加でき、`EMFILE`等でownerも巻き込めます。Nodeもsocket timeoutの既定・意味をそのように定義しています。[Node HTTP documentation](https://nodejs.org/api/http.html#servertimeout)

対策は「manifestだけ除外」ではありません。IPAが拒否されれば結局installできません。

- 非ownerの同時IPA転送数を小さく制限
- 非owner全体にもglobal concurrency cap
- 転送には絶対wall-clock期限
- owner identity/許可端末用の予約laneは429にしない

失敗installは、途中切断後のIPA再GETや`Range`再開という形になります。Appleが上限を契約しているわけではないため、120という推測よりowner laneで安全性を作る方が堅いです。
