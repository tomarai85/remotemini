# 証拠 — 一覧のメタキャッシュ修正 (2026-08-27)

commit `23cb47a`。本番 friday(`com.fleet.rc-backend`)へ配備済み、exit 0。

## 何が壊れていたか

`GET /api/sessions` が **2行の一覧を出すのに毎回 10,303 本の jsonl を読み直していた**。
キャッシュのヒット率は **0%**、5要求連続で `files=10303 read=10303 cached=0`。

原因は2層:
1. 上限 4,000 < 走査対象 10,303。走査は毎回頭から回るので、**LRU は「次に要る物を
   必ず直前に捨てる」= 構造的にヒット率0**。
2. 鍵に `size`/`mtime` が入っていたので、追記のたびに別 entry が増え、古い版が残る。
   上限を上げるだけでは、書き込みの多い機体で余白が版に食われて同じ雪崩が戻る
   (Codex 2026-08-27 の指摘。私の見落とし)。

## 実測

### サーバ側(friday の実データ 10,305 本)

| 条件 | 応答 | read | cached | rss 増分 |
|---|---|---|---|---|
| 修正前(上限 4000 固定) | **470-540ms 毎回** | 10303 | 0 | +136MB |
| 実験(上限 40000) | 冷 537ms → 温 60ms | 0 | 10303 | +93MB |
| 修正後(観測値から自動) | 冷 500ms → **温 58-61ms** | 0 | 10305 | +108MB |

★上限 4,000 のままは**遅い上にメモリも多い**(毎回1万件を読み直して捨てるため)。
「大きいキャッシュ = 重い」は実測で反証された。

### 電話と同じ URL 越し(`https://desk.tailnet.example:9443`)

| | 修正前 | 修正後(本番) |
|---|---|---|
| `/api/sessions` | 0.68 - 0.78s | 冷 0.75s → **0.22 - 0.32s** |
| うちサーバ側(本番ログ `ms=`) | 533 - 553 | **91 - 96** |
| `/healthz`(網だけの原価) | 0.19 - 0.31s | 0.12s |

**残り時間の主たる項は網の往復に移った**(サーバ側は全体の約4割→約4割以下)。

### 境界条件

- `limit=1` で打ち切った直後 → `examined=6 掃除=0 占有=10305`、
  **その直後の全件要求も `read=0` / 0.060s**。部分走査がキャッシュを汚さない。
- 冷えた初回で警告は出ない(誤報しない)。本番ログの警告件数 = 0。
- 行数は全条件で常に 2。**内容は一切変わっていない**。
