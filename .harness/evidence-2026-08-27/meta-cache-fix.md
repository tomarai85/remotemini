# 証拠 — 一覧のメタキャッシュ修正 (2026-08-27)

commit `23cb47a`。本番 friday(`com.fleet.rc-backend`)へ配備済み、exit 0。

## 何が壊れていたか

`GET /api/sessions` が **2行の一覧を出すのに毎回 10,303 本の jsonl を読み直していた**。
キャッシュのヒット率は **0%**、5要求連続で `files=10303 read=10303 cached=0`。

原因は2層:
1. 上限 4,000 < 走査対象 10,303。走査は毎回頭から回るので、**LRU は「次に要る物を
   必ず直前に捨てる」= 構造的にヒット率0**。
2. 鍵に `size`/`mtime` が入っていたので、追記のたびに別 entry が増え、古い版が残る。
   上限を上げるだけでは、書き込みの多い機体で余白が版に食われて同じ雪崩が戻る
   (Codex 2026-08-27 の指摘。私の見落とし)。

## 実測

| 実験(上限 40000) | 冷 537ms → 温 60ms | 0 | 10303 | +93MB |

「大きいキャッシュ = 重い」は実測で反証された。

**残り時間の主たる項は網の往復に移った**(サーバ側は全体の約4割→約4割以下)。

# 2026-08-28 — 「一番大きい数字」と「Tom が待たされる数字」は別物だった

## 測った物

## なぜ待たせないのか(実装で確認)

- `AccountBar` は `ListView` の **toolbar** に在り、自前の `.task { await viewModel.load() }` で
  描かれる。一覧の描画は口座の応答を待たない。→ 1243ms は**画面の外**の数字。
- `poll` は**長ポーリング**で、最大 20 秒まで保持してから返る。645ms は「保持していた時間」で、
  利用者の待ち時間ではない。返るのが遅い = 遅い、ではない。

## `/api/account` の揺れの正体(参考。直さない)

放置時間に比例して冷える = 台本と token file がページキャッシュから落ちる分。
温 141ms は台本自身の原価(167ms)とほぼ一致するので、上乗せは全部 I/O の冷え。
**直さない理由**: 画面の外の数字で、直す代償(短い TTL のキャッシュ = 口座名が古くなる /
定期的に叩いて温める = 毎分の subprocess)が、得られる物に見合わない。
★口座名を古く見せるのは既に設計が明示的に拒んでいる(`SettingsView` の注記)。

## ★教訓

**最大の数字を選ぶのは、критический path を選ぶ事ではない。**
数字を並べたら、次に問うのは「大きいか」ではなく「**利用者はこれを待っているか**」。
今回は実装(toolbar + 独立 `.task`)を読んで初めて分かった —— 数字だけ見て着手していたら、
