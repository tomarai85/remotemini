CONTEXT. A native SwiftUI iPhone app talks to a self-hosted backend over a private tailnet.
Sprint 2 builds the "session list" screen only. GET /api/sessions returns (observed live, 39 rows):
sessions[]: id, project?, cwd, title, lastPrompt?, turns?, metadataIncomplete, updatedAt,
fromRegistryOnly (present in only 1 of 39), live (a 3-way union keyed on `route`:

RULING 1 — do not decode `live` at all in Sprint 2. Rationale: we don't render it; a union

RULING 2 — the spec defines "backend unreachable" as 3 CONSECUTIVE failures (connection refused /

RULING 3 — for XCUITest fixtures, do NOT stand up a localhost HTTP server (that would force an

────────────────── 返ってきた答え(全文) ──────────────────

- **Ruling 1: Keep.** Omitting `live` is safer than inventing a knowingly incorrect model. Add
  one decoding test proving sessions still decode when `live` is missing or has any observed
  route.

- **Ruling 2: Wrong as written.** On a cold-start failure there is no previous list to preserve,
  so failures 1–2 produce an undefined screen. Separate initial-load failure—show an immediate
  full-screen retry state—from refresh failure with stale data. Also, foreground fetches are not
  explicit user retries, and cancellations must not increment the counter.

- **Ruling 3: Core approach is sound; justification and control are weak.** A localhost server
  does not inherently require a production ATS exception; test-specific build settings are
  possible. Use a dedicated `UI_TESTING` compilation condition instead of generic `DEBUG`. Binary
  string scanning is brittle; the required control should verify that a Release build ignores
  `RC_UI_FIXTURE` and cannot instantiate the fixture source.

- **Missing fourth ruling:** define `paneFault`. A `200` response with sessions plus
  `paneFault != nil` is neither a transport failure nor clean success. Specify whether it resets
  the failure counter and what warning, if any, appears while retaining the list.
