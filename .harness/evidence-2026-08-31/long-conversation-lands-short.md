# 長い会話が「最新の3行手前」で止まる —— 断続的な赤の正体(2026-08-31、実物を捕獲)

## 何が判ったか

`ConversationUITests.testOpeningALongConversationLandsAtTheNewestLine` の断続的な赤は
**検査の欠陥ではなく、実物の欠陥**だった。今朝 仕込んだ失敗時の記録が初めて発火し、
倒れた瞬間の画面が取れた。

```
conversation.loadEarlier   exists = true      ← 画面は正常に出ている
conversation.composerField exists = true
line 031 exists = false
line 090 exists = false                        ← 最新の行が**存在しない**

ScrollView            {{0.0, 110.0},  {375.0, 501.7}}
  内容 Other          {{0.0, -2430.7},{375.0, 3308.0}}
実在した行: line 068 … line 087(20 行)
```

## 読み方

- 内容の高さ **3308**、可視 **501.7**、寄せ **-2430.7**
  → 見えている範囲は内容の y ∈ [2430.7, 2932.4]
  → **下端まで 375.6pt 残っている**
- 実在する行は **068〜087** で止まり、**088/089/090 は作られていない**
  (`ScrollView` は窓の外の行を materialize しないので、`exists=false` は
   「其処まで寄っていない」の別表現)

### ★訂正(2026-08-31、批評で捕まった)—— 「おおよそ 3 行」は誤り

初版は 375.6pt を「おおよそ 3 行ぶん」と書いた。**倍以上の過小**。

```
3308 = 16(上padding) + Σ行 + 60*16(間隔) + 1(錨) + 16(下padding)
  → Σ行 = 2315 → 1行 38.6pt → slot pitch = 38.6 + 16 = 54.6pt
  → 375.6 / 54.6 = 6.9 → 約 7 行分
```

3 という数は「088/089/090 が作られていない」から来ていて、
**実体化していない行数と、足りない距離を1つの数に混ぜていた**。
実際に見えていた帯は 075-084 で、085/086/087 は**作られているが画面の外**。
`LazyVStack` は窓の外へ先回りして作るので、「作られている」と「見えている」は別。

つまり「開いたら一番新しい行へ寄る」動きは**走っているが、最後まで届いていない**。
画面も履歴も正常で、**寄せ先だけが 3 行手前**。

## 何故 断続的か

### ★撤回した仮説(2026-08-31)—— 「行の高さが可変なので推定が外れる」

初版は「寄せ先を決める時点の高さと、寄せ終わった後の高さが違う」と書いた。**此の画面では偽**。

- fixture の 60 行は `HistoryFixture` の `longTail` = `(31...90).map(line)` で、
  **全行 1 行・偶数 assistant / 奇数 user の完全交互 = 高さは 2 値**。
  2 行 materialize すれば推定は確定するので、内容の 11.4%(375.6pt)もの
  推定誤差が出る余地が無い。**倒れた実物は変高コンテンツではない。**

### ★算術で殺せた仮説 —— 「窓が着地後に縮む(帯 / 入力欄)」

機体 375x812、`ScrollView` の origin y = 110 → viewport の上限は **702**。
375.6 縮むには着地時に 877.3 が要り、窓を超えるので**単独では不可能**。
寄与しうる上限は 702 - 501.7 = **200.3pt** で、残り 175.3pt 以上は別の原因。

### 残る本命 —— 寄せの反復が完走していない

錨は 44 行ぶん下に在り、`scrollTo` は「実体化 → layout → 位置を測り直す」を
反復して寄って行く。混んだ機械では此の反復が run-loop の予算で打ち切られ、途中で止まる。

観測 3 点と全部 合う: (i) 負荷依存(競合ではなく予算枯渇)/ (ii) 推定誤差でなく
**大きく**(7 行)外す / (iii) 単独走行では予算が尽きないので必ず緑
(単体 3/3 緑・class 単独 緑・全掃き FAIL/FAIL/PASS/PASS/PASS)。

**★但し之も仮説であって観測ではない。**下記の通り、再現はまだ取れていない。

## ★★再現の試み —— 2 通りとも失敗(2026-08-31)

`ios/tools/conversation-landing-stress-control.sh` を作り、**直す前のコード**
(`git checkout` で修正を外した木)に対して 2 通りの負荷で 5 回ずつ撃った:

| 負荷の模型 | 結果 |
|---|---|
| `yes` を 15 本(論理コア 15 = 飽和) | **5/5 PASS** |
| 上に加えて、別 simulator(`iPhone-controls`)で `ConversationUITests` を回し続ける | **5/5 PASS** |

= **意図的に再現できていない。**従って、修正版が同じ計器で 5/5 緑でも
**それは修正が効いた証拠にならない**。機械を混ませる事と、
アプリの main run-loop の予算を枯らす事は同じではない、という所まで判っている。

## 何を巻き込んでいたか(此の欠陥の costs)

`ios/tools/conversation-ui-control.sh`(会話画面の変異対照)は**基準の走行が緑でないと
何も測れない**造り。此の赤が基準を落とすので、対照は
`PASS 0 / FAIL 0 / UNMEASURED 1` を返す —— **会話画面の4つの主張を守る対照が丸ごと死ぬ**。
2026-08-31 の全掃きで実測(其の 79 秒の走行が此の記録を残した)。

## 利用者から見た形

長い会話を開くと、**時々 最新より 3 行手前に着地する**。其の 3 行は描画すらされていない

105 → 116 で 0 file 変更)。
