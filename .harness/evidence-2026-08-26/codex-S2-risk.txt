PRODUCT: a phone app that displays approval prompts coming from a terminal AI agent on a Mac. Today every prompt looks identical — the same y/n card — whether the agent wants to list a directory or wipe a disk. Documented incident in my research: someone approved a database column drop from mobile while distracted.

WHAT I BUILT: a server-side pure function classifyRisk(texts) -> {tier, signals}. It regex-matches the prompt's own head lines + option labels + digest for known dangerous patterns. Three tiers: danger (recursive delete, DROP TABLE/COLUMN, TRUNCATE, DELETE FROM without WHERE, history-rewriting remote writes, hard reset, disk wipe, service unload, secrets/.env/private key, chmod 777, sudo, curl-pipe-shell), caution (ordinary remote write, package publish, production rollout, schema migration, outbound message send), unmatched (nothing matched). The tier only RAISES — a non-matching rule never lowers a tier already raised. It rides along in the existing choice payload as choice.risk and the phone paints a colored band above the prompt.

EXPLICIT NON-GOALS I ENCODED: (1) it changes nothing about what may be pressed — the server's existing 'keys' list still solely decides that; (2) the 'unmatched' tier returns an EMPTY user-facing notice, specifically so no layer can render it as 'safe'; a test asserts no tier's notice contains the word safe.

QUESTIONS:
1. Regex over prompt text is obviously defeatable and incomplete. Given the non-goals above, does shipping this make the user MEASURABLY safer, or does it create a false sense of security that is net-negative? Argue the strongest case against shipping it.
2. Which single missing pattern would you add first, and why that one?
3. Is 'raise only, never lower' actually the right monotonicity, or does it produce alert fatigue that ends with the user ignoring danger bands?
4. The classifier runs on the SERVER and the phone just paints. Any argument the classification belongs on the phone instead, or duplicated?

1. Shipping it is not yet “measurably safer”; that requires approval-error testing. Strongest case against:

- No band will inevitably be interpreted as “safe,” despite the empty notice.
- The classifier judges attacker-controlled presentation text, not the canonical operation.
- Indirection bypasses it: scripts, aliases, encoded commands, variables, chained commands, or dangerous content outside scanned lines.
- Broad matches such as `sudo` and `.env` create false positives and habituation.
- Color alone is weak under distraction and for accessibility.
- A prominent band may make unbanded prompts receive less scrutiny than today.

Treat it as “known hazard detected,” never as a risk verdict. Show “risk not assessed” for unmatched prompts if testing confirms that wording does not itself cause fatigue.

2. Add `\bDROP\s+(DATABASE|SCHEMA)\b` first. It has catastrophic blast radius, low false-positive risk, and closes an obvious gap beside the existing table/column rules.

3. Raise-only is correct within one classification: the maximum matched severity should win. Alert fatigue comes from overbroad rules, especially `sudo`, not monotonicity. Do not make severity sticky across revised prompts; recompute from the current canonical request.

4. Keep authoritative classification on the server. Duplicating identical regexes on the phone creates version drift and inconsistent warnings.
