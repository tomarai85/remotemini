1. Sleeping observer / staleness

- Misses any outage that begins and recovers entirely between observations, especially during sleep.
- A continuing outage is not detected until wake plus three failed runs: roughly 20–30 minutes after monitoring resumes.
- For the first 3600 seconds after the last successful check, stale data can still be reported as healthy.
- After 3600 seconds, `--report` correctly returns UNKNOWN, but only if something actually runs and respects its exit code. The JSON `status:"up"` remains misleading to direct readers.
- Staleness is therefore necessary but not sufficient. Monitoring absence itself should become an alert, generated by an always-on third party—not by the sleeping laptop.

2. Threshold / sleep / clock changes

- An outage entirely contained within sleep receives no notification.
- An outage that persists through wake receives no notification until three post-wake failures.
- Short or intermittent failures that never produce three consecutive observations are never notified.
- Overlapping runs can both observe `fails==2`, write `3`, and send duplicate alerts; alternatively, lost updates can delay or prevent reaching 3.
- Wall-clock jumps break age calculations: backward jumps can make old state appear fresh; forward jumps produce premature staleness. Treat negative age as UNKNOWN. Use monotonic time within a process, though cross-run freshness ultimately needs wall time plus sanity checks.
- Staleness currently changes only `--report`; it does not send an “observer missing” notification.

3. Health body

Require HTTP 200 plus successfully parsed JSON with at least:

- `ok === true`
- `pid` is a positive integer
- `uptime` is finite and nonnegative
- `version` is a nonempty string, preferably the expected deployed version

Also add a fixed service/instance identifier, such as `"service":"my-node-service"`, to detect a wrong backend, proxy fallback, or cached response. Reject oversized, malformed, or unexpected bodies and disable caching for `/healthz`.

4. State-file races

- `tempfile + os.replace` prevents readers from seeing partial JSON. `--report` sees either the previous or new complete file.
- It does not make the read-modify-write sequence safe across overlapping runs. Lost failure increments, status regression, duplicate threshold alerts, and duplicate recovery alerts remain possible.
- Use an inter-process lock covering read, probe-result transition, write, and notification decision; or make launchd invocation acquire a nonblocking lock and exit if another run exists.
- Ensure each writer uses a uniquely named tempfile in the same filesystem, then flush/fsync before replacement if crash durability matters.
