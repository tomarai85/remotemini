The original script only exists on a machine that is gone. The replacement machine has a different tool, `cswap`, with `cswap list --json` and `cswap switch <num|email>`. I wrote a shim translating cswap's JSON into the legacy text format the server's parser expects:
  現用: <name>            (or 「現用: (未設定)」)
  優先順 (.order):
  ->  1. name   トークン:有
      2. name   トークン:欠
Parser regex on each row: /^\s*(->)?\s*(\d+)\.\s+(.*?)\s+トークン:(有|欠)$/

SHIM BEHAVIOUR:
- exec cswap switch "$1" when given an arg.
- else: raw=$(cswap list --json); pipe into python3 that reads accounts[], uses a['email'] as name, a['number'] as order, active = bool(a['active']) or number == d['activeAccountNumber'], and prints 有 unless usageStatus is one of no_token/missing_token/token_missing (then 欠).
- Deliberate choice: cswap often reports usageStatus='keychain_unavailable' meaning the key could NOT BE READ, not that a token is absent. I map that to 有, reasoning that mapping it to 欠 makes the phone UI say 'this account cannot be switched to' which is a FALSE refusal; the real failure should surface at switch time instead.
- Non-zero exit on: cswap missing, list failing, empty output, unparseable JSON, accounts not a list, row not an object, number not an int.

QUESTIONS:
1. Is the keychain_unavailable -> 有 choice defensible, or does it create a worse failure than the false refusal it avoids?
2. Can any real email or account name break the row regex or the fixed-width '%s %2d. %s   トークン:%s' formatting (e.g. names with spaces, unicode, very long, leading '->')?
3. `exec cswap switch "$1"` — any injection or arg-confusion risk given $1 comes from an HTTP request body (server validates name length<=64 and rejects leading '-')?
4. Anything that could make this silently return a WRONG-but-parseable listing rather than failing?
