## 1. 経路側 `R-n`

**分母 = `rc-backend/src/*.mjs` 全 19 file(6,867 行)を、名前を挙げた5つの危険型で走査。**
走査したのは次の5型で、それ以外は見ていない:
① 同期の子プロセス(`execFileSync`)の時間の上限、② `|| true` / `?? true` 型の
fail-open 既定、③ 要求本文の大きさの上限、④ `JSON.parse` の保護、
⑤ 外部スクリプトへの依存。**行ごとの通読はしていない** —— 型を決めて横断した。

### R-1. 同期の子プロセスに、時間の上限が**一つも**無い(19 file 中、該当 4 経路) —— **当てた(S8-9)**

- **観測**: `execFileSync` を呼ぶ経路は4つ —— tmux 実行器(`makeTmuxRunner` の
  `call`)、`ps` の実行器、`/api/account`、`/api/account/next`。
  4つとも渡している option は `encoding` と `env` だけで、**`timeout` が無い**。
- **事象**: 子が固まると Node の event loop ごと止まる。止まるのはその要求だけでは
  なく**サーバ全体**で、`/health` すら返らなくなる。
- **これは推測ではない**: `server.mjs` 自身のコメントが、別件(e2e の対照が
  12回中12回赤になった件)の原因として「`execFileSync` で event loop ごと止まるので、
  負荷が乗るほど到着が散る」と**既に書いている**。同じ性質を、上限が無い状態で
  本番の hot path(poll ごとの tmux 呼び出し)が踏んでいる。
- ~~**渡米との関係**: 固まった時に効く手が「机で殺す」しかない。8/20 以降その手は無い。~~
  **↑ 誤り。訂正(2026-08-08、当てた後に自分の書類で反証)**: `PRE-DEPARTURE-2026-08-20.md`
  は同じ書類の中で2箇所、復旧手段を「渡米先からでも Blink 経由で ssh して開き直せる」と
  書いている。iPhone から ssh する経路は在る(Blink 自作版、2026-07-30 に実機7通りで検証済)。
  **正しい severity**: 固まっても電話から ssh で殺して開き直せる。効かないのは tailnet 自体が
  落ちた時だけ(同書類が既に「復旧用の ssh も同じ経路なので同時に死ぬ」と書いている)。
  本当の代償は「回復不能」ではなく「**人が気付いて ssh するまで電話が死んでいる**」。
  だから優先順位は上限そのものより**気付く手段**(= 外向きの生存監視)の方が高い ——
  そちらは別項目に起票した。★監査の重大度は、その場の印象ではなく**既に在る回復手段を
  数えてから**書く。書いた時に手元に在った書類を読み直していれば防げた。
- **直し方**: 4経路の option に `timeout` と `killSignal` を足す。値は tmux と `ps` で
  違ってよい(tmux は poll ごとに走るので短く、外部スクリプトは長く)。
- **誰の仕事か**: 私。裁定は要らない。ただし**本番の挙動が変わる**ので単独の節にする。
- **結果(2026-08-08)**: tmux 2000ms / `ps` 5000ms / 外部台本 10000ms、全て `SIGKILL`。
  数字の出し方(電話の 8 秒・echo 予算 1500ms・Codex の帯の**交点**)と、
  上限では塞げない4種は DESIGN §2.59。`run()` と `psSnapshot` は**触っていない** ——
  どちらも既に「判らない」へ倒れる形になっており、要ったのは諦める時刻だけだった。

### R-2. 外部スクリプト依存が2経路、しかも中身が repo の外(R-1 の中で最も深い) —— **当てた(S8-9)**

- **観測**: `/api/account` と `/api/account/next` は `FLEET_ACCOUNT` を同期で叩く。
  この script は repo の中に無いので、**版管理の外の物にサーバの応答性が繋がっている**。
- ~~**R-1 と分ける理由**: 直し方が違う。R-1 は上限を足せば済むが、此処は上限に達した
  時に電話へ何と出すかを決める必要が在る(「口座が読めない」は電話に出る文になる)。~~
  **↑ 誤り。訂正(2026-08-08、実測)**: **電話はこの道を1回も呼ばない**。
  `ios/Sources` / `ios/Tests` / `ios/UITests` を `account` で走査して当たるのは
  `KeychainCredentialStore` の属性名2箇所だけで、道の呼び出しは0。呼ぶのはサーバ自身が
  埋め込んでいる HTML と e2e と書類で、口座の切り替えは spec で v1 の対象外。

## 2. 体験側 `X-n`

**分母 = 2026-08-08 に simulator で実際に撮った3枚**(割り込み中 / 打鍵中 / 送信中)。
撮影経路は `ios/UITests/InFlightUITests.swift` の3本で、`xcresult` から取り出して
1枚ずつ**目で見た**。

**分母の外**(= 今回見ていないので、緑とも赤とも言えない): 一覧画面、鍵入力画面、
選択カードが**押せない**時の面、履歴を遡って読んでいる最中の面。

### X-1. 打鍵中、押した鍵のスピナが**伏せられたボタンと一緒に薄くなる**

- **観測**: スピナはボタン label の中に確かに出ていて、押した鍵にだけ出る
  (`spins(key:inFlight:)` は画面まで届いている)。だが `choiceEnabled` が飛んでいる間
  **両方の鍵を伏せる**ので、スピナも一緒に淡くなる。
- **なぜ問題か**: 「どちらを押したか」を持っているのは文ではなくスピナだけ。
  その唯一の手掛かりが、最も見えにくい状態で出る。
- **直し方の候補**: 押した行だけ不透明を戻す / 行の左に印を残す / 文の側に鍵の名を書く。

### X-2. CHOICE 画面に、ほぼ同じ結びの理由文が**2つ縦に並ぶ**

- **観測**: `interruptDisabledReason` と `composerDisabledReason` が同時に出て、
  どちらも「下の選択肢から選んでください」で終わる。電話の幅では2行×2で、
  **選択肢そのものより理由の方が高い**。
- **#28 との関係**: `interruptAllowedOnChoiceScreen` が Yes になると片方が黙るので、
  この項目は**#28 の裁定と束ねて扱う**。単独で文言だけ直すと二度手間になる。

### X-3. 「以前を読む」が灰色の `.bar` の**中**に描かれている(3枚とも)

- **観測**: 転写の続きを読む入口なのに、composer 側の道具に見える位置と背景に居る。
- **直し方の候補**: 転写の下端に置く / `.bar` の外へ出す。

### X-4. 送信が飛んでいる間、composer は生きていて打ち足せる → **当てた(S8-8)**

- **観測**: 送信中の写真に本文 `ping` が残っていた。残るのは設計通り(分類が
  終わるまで本文に触らない)。問題はその次で、`composerEnabled` は `isSending` を
  見ていないので**30 秒の間ずっと打ち足せる**。そこで成功が来ると `draft = ""` が
  走り、**一度も飛んでいない文字まで消えていた**。
- この監査で唯一、当てた項目。詳細は `DESIGN.md` §2.58。

### X-5. 転写が上詰めで、行が少ない時にボタン列との間に大きな空白が出る

- **観測**: 4行しか無い fixture では、転写の下に画面の3分の1ほどの空白。
  会話の道具としては下詰め(新しい行が下端に来る)が慣習。
- **直し方の候補**: 常に下詰め / 行が画面より少ない時だけ下詰め。
- ★弱い項目である事を書いておく: 分母が「4行の作り物」1つなので、実際の会話の
  長さでどう見えるかは**測っていない**。

### X-6. 所見ではなく方法の記録 —— 「見付けた欠陥」が**見に行ったら無かった**

- 縮小した写真では、割り込み中の1枚の状態バーの隅にスピナ状の点が見えた。
  切り出して4倍に拡大したら、そこに在ったのは**時計の表示だけ**で、点は無かった。
- 拡大しなければ「画面の隅に迷子のスピナが出る」という**存在しない欠陥**が1件、
  この一覧に残っていた。撮る事と**見る事**は別の作業である、の実例。
