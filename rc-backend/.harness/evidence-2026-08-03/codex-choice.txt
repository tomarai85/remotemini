## Context

I run Claude Code sessions inside tmux panes on a Mac mini. A small self-hosted HTTP backend lets my iPhone view those panes and inject keystrokes while I travel. Panes are classified into screen states; one of them is CHOICE = "a numbered selection menu is on screen" (e.g. `/model`'s model picker, or a permission confirmation dialog "Do you want to proceed? 1. Yes 2. Yes, and don't ask again 3. No").

The owner's standing ruling, verbatim: 「自動化に安全確認を押させない」 = the automated instrument must never press Claude Code's security/trust/permission confirmations. A separate design decision (D4) says permission dialogs are "notify the phone only, no approval button".

Until now the phone could SEE a CHOICE screen but could not send anything. I just shipped a way to answer benign menus.

## What I built

`POST /api/sessions/:id/choice` with body `{key, digest}`.
- `key` ∈ `"1".."9" | "enter" | "escape"`. Anything else → 400.
- `digest` is REQUIRED. If absent → 400. The server deliberately does NOT fill it in from the current screen.

Pipeline inside one per-pane mutex:
1. capture the pane ONCE.
2. classify the screen; if not CHOICE → refuse.
3. parse the menu into a structure: head text, list of `(n, label)` option rows, cursor position, footer line, and whether the composer (input box) is drawn.
4. classify the menu against an ALLOWLIST of matchers. Today the allowlist has exactly ONE entry: `select-model@1`, whose test is `head.includes("Select model") && /Enter to set as default/.test(footer)`, and which permits key kinds `digit | enter | escape`.
   - allowlist hit → `benign` (+ the matcher's permitted key kinds)
   - a separate HARD_STOP regex hit (e.g. /Do you want to proceed\?/) → `hard-stop`
   - anything else → `unrecognized`
5. compute `digest` = a hash over the PARSED SEMANTIC FIELDS (pane id, "CHOICE", kind, matcher@version, head, the `n|label` sequence, cursor index, footer, composer-absent) — deliberately NOT a hash of the raw screen text, and deliberately NOT an aggressively normalized screen.
6. refuse unless kind === benign; refuse unless the key kind is in the matcher's permitted list; refuse unless the caller's `digest` equals the computed one (409 + the current digest is returned so the caller can retry).
7. send `tmux send-keys -t <pane> -l -- <n>` (literal). For `escape`, wait 150ms afterward INSIDE the mutex (terminals can read Esc + next byte as an Alt sequence).
8. re-capture; report `applied: "verified"` only if the screen left CHOICE or the digest changed, else `"unverified"`.

Extra guard: if the composer/input box IS drawn while the screen looks like a menu, refuse as `unrecognized` — because the only signal separating "a real live menu" from "an echo of a menu in scrollback history" is that menus do not draw the composer. If that invariant is violated, I do not know what I am looking at.

I explicitly claim: **the safety of this does NOT depend on the HARD_STOP regex.** HARD_STOP only supplies a human-readable reason. Even with every hard-stop phrase stripped from a real permission dialog, the screen is refused as `unrecognized`. I have a test that strips those phrases and asserts refusal, plus a mutation (C1) that degenerates the allowlist into a denylist and must be caught.

Not shipped: sending `escape` (= an explicit decline) to non-benign screens. I think it should be allowed (it is the only way to unstick a stuck session while traveling, and its direction is always refusal, never approval), but I am leaving it to the owner to re-define D4.

1. permission が `benign` になる経路はあります

`select-model@1` は画面の出自ではなく、2つの文字列だけを認証しています。これは allowlist ではなく、衝突しやすいテキスト署名です。

- option の個数・番号・ラベルを検証していないため、実際の選択肢が `1. Yes / 2. Yes... / 3. No` でも通ります。
- permission に表示されるコマンドや説明が未信頼入力なら、改行やANSI制御文字によって `head` と `footer` を偽装できます。tmux capture が見るのは「描画後のセル」なので、元の文字列境界は失われます。
- ファイル内容やツール出力が偽メニューを描き、composer がまだ戻っていない間に数字を送ると、その入力が後続のpermissionへ持ち越される可能性があります。
- allowlist判定がHARD_STOPより先なら、両方に一致する画面が即座に fail-open します。HARD_STOP優先にしても、出自認証の欠如は直りません。

git branch名単独での偽装は制約上難しくても、ツール出力・コマンド表示・ANSIを含む画面全体では成立します。

2. ONE-capture は実用上のTOCTOUです

現実的な事故列は次です。

1. モデルメニューをcapture。
2. 物理キーボード、別のtmux client、別API、またはClaude自身の遷移でメニューが閉じる。
3. permission dialog が表示される。
4. 保存済み判定に基づく `1` またはEnterがpermissionへ着弾する。

mutexが守るのは同じロックを使うコードだけです。tmux、Claude、物理入力は守りません。送信直前の再captureは窓を縮めるだけで、原子的なcompare-and-sendにはなりません。

全入力を所有するPTYプロキシ、またはClaude側が発行する画面世代ID付きの型付き操作APIがなければ、「このキーがこのメニューだけに届く」という保証はできません。

3. semantic digestには衝突があります

具体例は、同じhead・選択肢・cursor・footerの間に、未解析の説明行だけが異なる画面です。

- 画面A: 無害なモデル選択説明
- 画面B: 「この操作は危険なコマンドを実行する」という警告やpermission対象コマンドを含む

パーサーがその中間領域、ANSI属性、disabled状態、overlayを捨てれば同じdigestになります。semantic digestはUX上の変更検知には使えても、セキュリティ境界には不十分です。正規化を最小限にした画面全セルのhashも併用すべきですが、それでもUI偽装とTOCTOUは解決しません。

4. `unverified` の自動再送は危険です

200自体より契約が問題です。クライアントは絶対に再送してはいけません。

最初のEnterが入力キューに入ったまま再描画が遅れ、`unverified`になる。その後もう一度送ると、最初のEnterがモデル選択、二つ目が直後のpermission承認に使われ得ます。

必要なのは以下です。

- `unverified` は「結果不明、再送禁止」とする。
- request idによる厳密な冪等性を実装する。
- 一度送信したdigestには、明確な画面遷移を確認するまで二度と送らない。
- phoneは再captureして表示し、利用者の新しい明示操作を要求する。
- 409で返した新digestを自動採用・自動再送しない。

5. 追加の出荷拒否理由

- `1..9`を許すのに、その番号がモデル選択肢として存在するか検証していません。
- 「CHOICEを離れた／digestが変わった」は成功確認ではありません。permissionへ遷移してもverifiedになり得ます。
- digestはAPIから取得できるため、認可トークンではなく単なる鮮度ヒントです。
- Escapeは常に拒否とは限りません。dismiss、背後画面への復帰、後続入力とのAlt結合があり、mutex外の入力には150ms待機も効きません。D4が明示変更されるまでは禁止が妥当です。
- API認証、TLS、CSRF対策、replay防止が別途保証されていなければ、それだけでも出荷不可です。

絶対条件が「自動化に安全確認を押させない」なら、共有PTYへの文脈依存キー送信では達成不能です。モデル変更はClaudeの型付き制御面へ分離するか、現状どおり閲覧・通知だけに留めるべきです。
