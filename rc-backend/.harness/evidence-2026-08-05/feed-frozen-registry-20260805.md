# 配信が握っていた「1リクエスト分の登録簿」—— 本番の欠陥(2026-08-05 夜)

前の記録(`flaky-13Wa-rootcause-20260805.md` §6)に
「**追っていない。直っていない。**」と書いて残した 13-D の揺らぎを追った結果、
**検査の揺らぎではなく製品の欠陥**だった。

結論を先に:

| | |
|---|---|
| 症状(電話) | live の面を開いて **15 秒**で「ペイン登録をしていない」に落ち、**戻らない** |
| 真因 | `startFeed` に**リクエスト寿命の登録簿の写し**を握った閉包を渡していた |
| 直し方 | `startFeed` から解決関数の引数を消す(渡す口を無くす) |
| 栓 | e2e 13-Z(登録先の付け替えに配信が追随するか)+ 陰性対照 |
| 直した後 | e2e **269 / 0**、単体 **681 / 681** |

---

## 1. 出発点 —— 「負荷を掛けると赤くなる検査」

`13-D 土台: 選択待ちの画面が1枚来る` が、24 本の CPU 焼きを載せた 15 コア機
(loadavg 約 60)で **6 / 6 赤**。落ち方は 2 種類:

| 形 | `pc1.screen` | 落ちる項目数 |
|---|---|---|
| (1) | `{"route":"blocked","reason":"unregistered","candidates":1,"source":"registry"}` | 2 |
| (2) | `null` | 1(守られた `argCheck` は飛ぶ) |

## 2. ★最初の仮説は**測定で死んだ**(直す前に殺せた)

仮説: e2e 自身の心拍 `setInterval(beatOnce, 1000)` が負荷で飢え、
`HEARTBEAT_TTL_MS`(15 秒)を越えて登録が死ぬ。

切り出して単体で測った(24 本の焼き / 60 秒):

```
{"発火回数":59,"最大間隔ms":1003,"15秒超の回数":0,"p50":1002,"p90":1003,"p99":1003}
```

**書き手は 1 秒たりとも遅れていない。** 仮説は棄却。
ここで「まあ心拍だろう」と直していたら、症状を消して原因を残した。

## 3. 読み側に齢を言わせた —— 見分けの付かない 3 箇所に印を付ける

`registry.mjs` の `unregistered` を返す箇所は 3 つあり、
出力はどれも `candidates:1, source:"registry"` で**同値**。
写した木の `registry.mjs` に `probeSite` / `probeAge` を足し、
`blocked.mjs` の `blockedBody()` が欄を落とすので**そこにも**転送を足して走らせた。

| 実測 | 値 |
|---|---|
| 発火箇所 | `A252-dead-entry`(生きた登録が 1 件も無い枝) |
| 登録の**見かけの齢** | **22397ms / 26463ms** |
| 同時刻の書き手の最大間隔 | **1003ms** |

書き手は 1 秒ごと。読み側は 22〜26 秒前の物を見ている。
= **読み側が読み直していない。**

## 4. 真因 —— 寿命の違う 2 つを 1 本の閉包で繋いでいた

`poll` / `stream` のハンドラは登録簿を **1リクエストにつき 1 回**読む。
これは正しい(2 回読むと statusline が間に挟まって
「存在すると判定した直後の解決では別内容」になりうる)。

間違いは、その写しを握った `resolvePane` を `startFeed` に渡していた事。
配信の timer は**最初に建てた 1 本が生き続ける**ので、写しも生き続ける。
`registryCtx` は `now` を毎回取り直し、写しの `mtime` は凍っている
= **経過時間だけで齢が伸びる**。15 秒で全部が心拍切れに見える。

電話が poll を撃ち続ける限り配信は畳まれない = **戻らない**。

## 5. 直し方 —— 消音ではなく、賭けを構造から外す(13-W-a と同じ形)

- `startFeed(sessionId, file)` —— **解決関数の引数を消した**。
- `feedTick` が tick ごとに `livePaneFor(sessionId, cwdOfSessionFile(file), undefined, undefined)`
  を呼ぶ(= 登録簿を読み直す)。
- `livePaneFor` の `entries` 欄に「**1リクエストの中でだけ**渡してよい」を明記。
- ハンドラ側の `sessionCwd` は module 側の `cwdOfSessionFile` に出して共有。

写しを渡す口が無いので、同じ間違いを**書けない**。
代償は 1.4 秒に 1 回の登録簿読み直し —— 同じ tick で既に `ps` を起こしているので誤差。

## 6. 栓(13-Z)—— 時間を待つ検査にはしない

「15 秒待って生きているか」で書くのは**同じ病気の再発明**。
代わりに**登録先を付け替える**:

1. `%28` に登録した会話を poll(配信が建つ)→ 1 枚撮れるまで待つ。
2. 登録を `%29`(別の画面種別)へ付け替える。心拍は打ち続ける = 生きた登録。
3. **`%29` が来るまで**撃ち直す。凍った写しなら永久に来ないので回数を使い切って赤。

凍った写しなら `%28` を出し続ける。待ち時間を延ばしても壊れる側には倒れない
(写しは待つほど古くなるだけ)= 遅い機械が偽の緑を作らない向き。

### 6-b. ★書いた初版が**同じ病気**だった(2 回踏んだ)

初版は「登録を付け替えて `sleep(3000)` してから見る」だった。
loadavg 90 の機械で走らせたら `screen: null` で赤 —— **1.4 秒に間に合ったか**を
測る検査になっていた。同じ走行で 13-D も `null` で落ちた。理由は別で、
`13-D` は「**遥か上の節で建てた配信がまだ生きている**」に賭けていた
(`POLL_LEASE_MS = 30_000`。間の節が 30 秒を超えると `stopFeedIfIdle` が
`f.screen` を `null` にする)。

どちらも眠りを消して直した。道具は `pollUntilScreen`:

- 保留中の poll は `feedBroadcast` が起こす。ただし起こす口は screen 専用ではない ——
  配信の 1 tick 目は転写に繋いだ印(`tail-attached` の gap)を出すので、
  **待ち受けは画面より先にその item で返る**。1 回で諦めると `screen: null`。
- なので栞を繋いで撃ち直す。遅い機械は**回数ではなく待つ時間**が伸びるだけ。
- `want` を渡すと「その画面が来るまで」。`windowMs` は観測窓が埋まるまで tick ごとに
  伸びるので、**画面が変わった ≠ 付け替わった**(1 回で判定すると `%28` のまま版だけ
  上がった枚を掴む)。ここを取り違えると検査が嘘を出す。

## 7. 「直った」の根拠

| 何を | 結果 |
|---|---|
| `npm test` | **681 / 681** |
| `node test/e2e-local.mjs`(通常負荷) | **269 / 0** |
| **★陰性対照**: 写した木で `startFeed` を元の形へ戻す | **13-Z だけが赤**(`screen: null` = `%29` が永久に来ない)。他 268 本は緑 |
| 負荷下 24 本 × 6 走(直した木) | **6 走とも 269 / 0、赤 0 / 6**。焼きの残骸 0 |

負荷下の 1 分平均は polling で観測した範囲で **60 → 112**。
★この数字は焼き 24 本だけの物ではない —— 同時に `mobileassetd` 76% / `assistantd` 35% /
`swift-frontend` 20% と、私の物ではない `yes` が走っていた(コマンド名だけで確認)。
**設計した負荷より厳しい条件で緑**であって、条件を薄めた結果ではない。

★陰性対照の落ち方が**1 本に絞られた**のが重要。
初版の検査では同じ陰性対照で 13-D も道連れで赤くなっていた ——
つまり 13-D は「配信が生きている事」と「登録簿を読み直す事」を**同時に**測っていて、
どちらが壊れたか検査文からは分からなかった。今は 1 検査 1 性質。

**負荷は原因ではなかった。** 経過時間を 15 秒の向こうへ押しただけで、
写しが凍っている限り遅かれ早かれ必ず起きる。
負荷試験が測っていたのは原因ではなく**露出条件**だった。

## 8. 一般化

**「1リクエストにつき1回だけ読む」最適化は、寿命の境界を跨いだ瞬間に嘘になる。**
凍った写しに `now` だけが進む構造は「時間が経つほど現実から離れる」を必ず作る。
写しを作る時は、**その写しが誰に渡るか**を**渡し先の寿命**で数える。

副産物: `src/*.mjs` の `setInterval` / `setTimeout` を全部数え直した(12 箇所)。
リクエスト寿命の物を寿命の長い側へ渡していたのは `startFeed` の 1 箇所だけ。

## 9. 触った file

- `src/server.mjs` —— `cwdOfSessionFile` を module へ抽出 / `startFeed` の引数削減 /
  `feedTick` が毎 tick 読み直す / `livePaneFor` の `entries` に寿命の条件を明記。
- `test/e2e-local.mjs` —— `SID_FEEDREG` + ペイン `%28` `%29` + 画面 2 枚 + 13-Z の 2 検査 +
  `pollUntilScreen`(眠りで待たない道具)+ 13-D の配信依存を外す。

**今回は `src/` に欠陥が在った**(13-W-a とは逆)。
